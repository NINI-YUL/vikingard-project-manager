# 配置库与管理看板产品原型决策

日期：2026-09-10

更新日期：2026-10-30

对应 Issue：#13

状态：已确认的后台页面与交互已实现，本轮一致性收尾和主要流程走查已完成；正式后台尚未实现。钉钉通知与 AI 表格接入另行验证。

## 原型问题与结论

本轮要回答的问题是：什么样的配置结构和看板布局，能让非技术项目负责人完成日常配置，并快速追踪版本、需求、风险和人员工作情况。

对比了三种可切换方案：A“行动驾驶舱”、B“配置工作台”、C“对象探索器”。最终不把三种方案建设成并列入口，而采用组合方案：

- A 作为默认首页，先呈现需要处理的风险、待协调人员、异常及指标可信度；
- B 作为独立配置库，集中维护系统默认、版本覆盖和需求级覆盖；
- C 的面包屑、父级上下文和横向信号矩阵吸收到统一对象详情中，树形浏览器不作为默认首页；
- 版本、需求、工作单和人员可保留父级上下文并继续下钻；各详情按对象职责展示必要信息，不强制采用完全相同的指标和侧栏。

## 已确认决策

### 配置库

1. 配置层级为“系统默认 → 版本覆盖 → 需求级覆盖”；下层只记录例外，未设置项继承上层。
2. 每个配置项必须展示生效值、来源层级、影响范围与变更记录；需求级覆盖支持恢复继承和保存前影响复核，不另走草稿发布。
3. 版本启用前展示同步起点、覆盖数量和预计影响对象；版本结束后停止同步、采集和通知，但保留历史查询。
   误选版本的“移除”仅限尚未产生任何同步、反馈或通知数据的版本；一旦有任一管理数据即不可移除。移除须填写原因并留痕，不删除 Teambition 版本，版本重新进入选择列表。已产生管理数据但误选时，在“结束管理”弹窗内选择第三种处理方式“误选，停止纳入”：记录原因，退出日常管理并停止常规同步、采集和通知，保留已采集事实及审计；不宣称版本已上线或停止开发，不进入完结版本或已上线历史。再次纳入须由管理员从“停止纳入记录”显式发起，重新核对当前工单结构、字段、状态、版本负责人、范围和规则，确认新的跟踪起点；原有数据和停止记录不删除，按工单 ID 延续当前事实，不重复计数，中断期间标记资料不完整，不推算过程或历时。恢复不等于首次纳入，也不自动回到普通候选列表。原型的快照复核摘要和同步结果只作演示，不代表 TB 实际读取通过。原型以“待首次同步”和“模拟首次同步”展示可移除边界；正式启用时须补齐已有工作单的当前结构与状态，不能因可移除窗口而省略首次同步。
   “已上线并结束”不因仍有未完成工单而一律阻止；版本负责人须先确认实际上线。每张遗留工单必须记录后续负责人和处理方式，否则阻止确认；未完成工单的实际完成时间保持空白，不因版本结束补造日期。没有可核对工单清单的版本不能将“未知”视为零；原型仅对有演示明细的版本展示逐项确认。
   业务风险不一律阻止上线结束，但每项未解决风险须明确后续负责人、处理方式并留存。影响上线事实、版本范围或未完成工单清单可信度的数据异常必须先核实，不能用“明确保留”绕过；其他数据异常须注明指标影响、负责人和后续处理方式后方可留存。受影响的历史指标显示“未知”或“不可计算”，不得填零。原型仅以演示清单和人工输入展示校验，不代表 Teambition 真实核对已完成；缺少可核对清单不得以无异常确认结束。
4. 状态语义映射按项目与工作流分组，保留原始状态 ID 和名称。新状态未映射时继续同步工作单，但暂停受影响的完成、历时、风险和通知。
5. 人员映射只由管理员确认。邮箱或手机号完全一致只能生成候选建议；仅姓名近似不得自动匹配。确认前禁止向候选人发送消息。
6. 「人员与通知」将身份映射、业务角色和系统权限合并到“人员与权限”页签，以单个人员为中心核对和维护；“通知对象”保留为独立页签，只读展示通知节点与接收规则。只有身份映射已确认的人员可以维护业务角色或被显式授予系统权限；业务角色仅参与通知条件，系统权限仅控制后台管理操作，二者不自动推定。角色或权限调整必须记录操作人、时间、前后值和原因；原型仅在当前会话演示，不代表真实钉钉身份或权限校验。
7. 系统权限只保留四档：无后台访问权限、查看者、系统管理员、系统所有者。查看者可查看管理看板、版本和历史但不可修改；系统管理员可维护配置、处理异常及执行版本管理；系统所有者可管理系统权限并包含系统管理员能力。最后一名系统所有者不可删除；该保护不以业务角色、Teambition 身份或版本负责人身份推定。
8. “通知对象”页只展示通知节点与接收规则，不再提供当前人员选择、逐人演示判断或“当前人员解析”。投递仍需确认身份映射、需求关系与节点触发；系统权限不增加通知资格，无法投递人员不自动由他人代收。具体收件人应在对应需求范围核对，不在通用规则页推算人数；核心需求详情的只读预览仅以显式演示参与关系与渠道状态展示规则命中及未纳入原因，不代表真实收件或已发送记录。

### 规则设置补充（2026-10-29）

- 按基线 RULE-01 使用三级作用范围、一个编辑弹窗和逐项继承。无特殊配置隐藏详情模块；保存立即更新会话配置，不走独立草稿发布；恢复继承须先确认影响并留痕。
- 三个节点统一为基础流程、细节完整、测试阶段：细节完整累计基础流程；测试阶段替代原全部内容完成，固定覆盖全部应处理后代，不等于实际上线。非交付终态单列，缺少职能工单须确认不适用，未知不得视为完成。
- 采集按公司时区与工作日历执行多个星期/时分组合；开发关注跨全部活跃版本统一使用系统阈值，默认 3 张，不提供版本或需求阈值覆盖。
- 前两个完成节点通知参与者中的测试、运营、策划、PM；测试阶段暂不新增完成通知。特殊通知对象配置入口暂缓；通用规则及需求只读预览保留。
- 原型编辑只演示配置，不声称已有真实完成判定、调度、投递或历史重算；负责人不适用确认和更正投递仍是正式系统规则，不虚构为本次新增可执行能力。

### 管理看板与异常

1. 默认首页按照管理行动排序，高风险、需关注、待协调人员、数据异常和数据覆盖率均可一跳进入对象详情或处理入口。
2. 业务风险、跟进风险和数据异常分别展示；人员并发关注是复核信号，不是绩效评分。
3. 风险展示当前等级、原因、影响节点、首次出现时间与持续工作日；解除后保留峰值和历史，不计算平均分。
4. “待处理异常”按状态未映射、人员待匹配、字段缺失或结构问题、同步失败和投递失败分组，展示编号、具体类型、对象、影响、发现时间、处理方和下一步；“审计记录”按时间倒序保留发现、重试、确认、修复和发布过程，两者通过异常编号关联。业务风险不混入数据异常。
5. 退出活跃管理的版本不进入默认行动队列；仅实际上线且选入留档的版本进入历史查询。未上线终止保留完结记录，误选停止纳入保留专门记录，均不进入已上线历史指标。
6. 映射配置完成不直接关闭异常；待受影响数据同步、计算或校验确认恢复后才移出待处理。同步或投递重试成功也移出待处理，过程继续保留审计；异常页暂不增加详情抽屉、审计分类或筛选。

### 下钻与数据覆盖率

1. 版本 → 需求 → 工作单保留父级上下文；人员是从需求和工作单交叉进入的管理视角。
2. 四类详情保留面包屑与对象上下文，但指标、管理信号、最近变化和配置入口按对象分别设计；人员详情不设独立“当前管理信号”，改为本人相关的“最近变化”。
3. 数据覆盖率与指标并列显示，必须提供“可计算记录数 / 应统计记录数”、缺失原因和规则允许的排除项。
4. 覆盖率不低于 90% 为正常，70% 至 90% 为数据不完整，低于 70% 为指标暂不可靠。缺失值不按零处理，也不解释为低进度。

### 需求时间线与工作日历

1. 需求详情的工单时间线使用按日展开的日期网格和按周分组表头，横向状态条展示开始、截止与当前状态；周末、节假日和特殊工作日使用不同底色。
2. 时间线展示八类核心专业子单和测试总单；未排期工单仍保留在时间线中但不绘制日期条，点击工单打开右侧详情抽屉。
3. 工作日历支持将周末集体加班配置为特殊工作日，并统一影响计划周期、逾期、三日内到期、开发历时和测试历时。
4. 需求详情不展示结构完成率；保留终态工作单数量，但不将其换算为交付比例。

### 人员详情

1. 左侧人员列表按职能分组，可向左收起，点击姓名切换右侧详情；不产生人员排序、评分或排名。
2. 顶部只显示在手核心子单、并发关注、已逾期和三日内到期的数量，辅助来源说明不进入指标卡底部。
3. 工单明细分别展示所属需求、版本、计划时间、Teambition 状态和有效反馈进度；计划时间用红、绿、常规字体区分逾期、三日内到期和其他情况。
4. 右侧只保留与本人相关的最近变化，不重复展示独立管理信号；统计口径以本人实际执行的核心专业子单为准。

### 历史查询复盘

1. 历史查询采用“版本总览 → 版本详情 → 需求详情”三层下钻，只统计当前选入留档且已确认实际上线的版本；热更版本可不纳入，留档范围调整必须记录操作人、时间和原因。
2. 版本总览标题为“版本历史数据”，展示版本数、版本周期中位数、按时上线版本和核心需求按时完成率。中位数分别对可计算版本的工作日周期和自然日周期求取，工作日为主值、自然日为辅助值，并展示样本数；缺少可信日期的版本不进入相应分母。
3. 版本详情展示工作日主值、自然日辅助值的版本周期，以及计划开始时间、计划上线时间和实际上线时间；所有核心需求纵向排列并可下钻，不限制需求数量。
4. 需求详情展示需求周期、开发阶段周期、测试阶段周期、计划完成时间和实际完成时间；时间线采用按周分组、按日展开的甘特样式，计划/实际/超期和完成节点分开呈现。开发阶段覆盖八类核心专业子单，测试与验收分节点，辅助子单不纳入开发阶段周期但影响最终交付。
5. 原始工作单明细按截图式单卡片平铺六列展示：环节、类型、计划起止、实际起止、实际时长、较计划；各列左对齐，说明置于表格下方，实际时长按工作日计算。
6. 版本首次计划基线在正式纳入管理时确认；正式改期不覆盖基线，录入纠错可经确认修正并留存旧值。实际上线前漏同步完成事实可经证据核实修正并重算指标；上线后完成或重开只作为后续变化。历史使用实际上线时生效工作日历，延期原因由显式授权系统管理员（通常为 PM）登记确认。
7. 历史复盘页暂不展示按需求量级分组的分布统计；该类统计若后续建设，仍按既有规则使用当前需求量级重算，不改变本页固定交付事实的口径。

### 人力参与度

1. 独立的年度堆叠条和月度甘特时间带展示人员关联核心需求的阶段，不等同于按当前在手核心专业子单展示的人员详情，也不表示个人实际投入工时、出勤或绩效。默认展示映射已确认且有效的全部人员，按当前职能筛选。
2. 人员从首次被记录为核心需求下处理人或测试人到明确移出或需求正式结束期间建立关联；同日多需求按开发、调优、空闲优先级归入一个主阶段。核心专业子单仍在开发为开发期；专业子单完成而测试、相关缺陷或适用验收尚未完成为调优期；没有进行中的关联核心需求为空闲期，仍可能处理其他工单。证据不足为未知，未来日期留白。
3. 年度条按公司工作日历统计所选年份的开发、调优、空闲天数，不显示工单数；当前年份同时显示全年工作日和截至演示截点已发生的工作日。月度时间带按日展开，显示一段连续主阶段的完成工单数，已结束为“共N张”，进行中为“ING N张”。
4. 工单只在真正进入交付完成态后计入完成时有效处理人或测试人的阶段；各类型实际工单可纳入，但纯容器、未完成及非交付终态不计数。连续阶段跨月、跨年时，所跨片段重复显示整段总数，不可相加成月合计；年度天数仍仅计所选年。月度页不展示本月工单合计或工作单详情。
5. 人员关联历史、拟新增的处理人/测试人字段及变更、完成时点、工作日历等是正式计算前提，尚未完成 Teambition 租户验证。原型人名、日期和工单数量仅用于评审；人员身份、业务角色和系统权限现已整合到“人员与权限”页，其交互口径见配置库决策及基线第 10 节。

## 当前阶段基线

行动中心、需求详情、工作单详情、版本详情、人员详情、异常与审计页、历史查询页及人力参与度的逐项交互基线、字段范围和变更编号见 `docs/product/config-dashboard-prototype-baseline.md`。后续原型调整必须引用基线编号；本决策记录的是原型阶段确认，不代表正式后台实现已经开始。

### 状态语义映射补充（2026-10-30 确认）

- 状态映射页按项目与工作流维护原始状态到七项统一管理语义的对应关系，保留原始状态 ID、名称和历史；“未映射”是异常状态，不作为可选语义。
- 页面采用逐状态表格加一个统一编辑弹窗。弹窗一次维护全部状态，并允许设置四类独立计时节点；保存前填写变更原因，保存后进入“待验证恢复”。
- 允许部分映射保存。未映射状态继续同步，但受影响的完成判断、开发/测试历时、风险和通知暂停，直至重新同步、计算或校验确认恢复；保存映射本身不关闭异常。
- 七项语义为：未开始、开发中、测试中、处理中，但不计时、暂停、交付完成、非交付终态。开发完成和测试完成是计时节点，不等于最终交付；缺少开始记录的历时显示未知或不可计算。

### 影响与恢复补充（2026-10-30 确认）

- 按 STATUS-02 接通映射保存、待验证恢复、验证失败、恢复成功的状态展示。剩余未映射问题必须明确列出，不能因部分保存就宣称恢复。
