# 第一版数据、登录权限与开发任务清单

日期：2026-11-12。状态：用户已确认的开发准备基线；用于后续开发拆分，不是已实现功能或正式建表结果。明确标注待实测或启用前确认的项目继续保留。

## 1. 给业务使用者的说明

第一版以已确认的总原型 v2 为目标，不重新设计已验收页面。先跑通一个测试版本从纳入、同步、通知、反馈到展示的完整流程，再补齐同一首版范围内的其他页面。分批实现不代表缩减第一版验收范围。

用户不需要审核数据库字段名或编写技术配置。业务上只需核对：系统保存什么、谁能查看或修改、异常如何处理。首位系统所有者及首批访问名单在登录启用前确认；不以“第一个登录的人”自动决定管理员。

既定分工：Teambition 保存工作事实；AI 表格收集反馈并承担已验证的通知中转；本系统保存配置、校验结果、业务历史、权限和审计。里程碑反馈留到后续版本。

## 3. 本系统需要保存的数据

下表为逻辑分组及建议表名，不要求每组对应一个页面，也不代表已经创建数据库表。代码与 SQL 在开发任务中落地。

| 业务内容 | 建议数据表 | 最少保存内容 | 关键约束 |
| --- | --- | --- | --- |
| 人员和身份关系 | people、identity_mappings | 本系统人员 ID、TB 用户 ID、钉钉可信身份 ID、企业范围、映射确认状态、停用信息 | 不按姓名或用户手填钉钉号自动合并；同一来源账号在企业内唯一映射，变更留审计 |
| 后台权限与登录 | access_grants、login_sessions | 本系统人员、四档权限、授权及撤销时间、授权人；会话摘要、到期和撤销状态 | 无授权默认为无后台权限；每次后台请求核验当前授权，不只在页面隐藏按钮 |
| 人员业务角色 | business_roles | 测试、运营、策划、PM 等业务角色及维护记录 | 不代替后台权限；实际执行者和参与者以具体 TB 工单为准 |
| 接入项目与来源配置 | source_projects、source_bindings | 企业、TB 项目、任务类型/字段/状态真实 ID、AI 表格与字段标识、配置版本 | 密钥只保存外部受限配置的引用，不在业务表、普通日志或浏览器中返回 |
| 版本管理 | managed_versions、tracking_periods | 来源版本标识、负责人、生命周期状态、同步起点、跟踪区间、上线事实、留档选择、停止/恢复原因 | 移除、停止纳入、未上线终止、已上线结束分开；恢复纳入新建跟踪区间，延续工单身份 |
| 任务当前事实 | work_items、work_item_participants | TB 内部 ID、可见编号、标题、类型、分类、职能、父任务、所属版本、执行者/参与者、计划、原始状态、来源时间、最近同步时间及数据可用性 | 内部关联使用 TB 稳定 ID；页面显示 vkt-64 类编号；父子关系不能形成循环，缺失不猜测 |
| 来源状态及计划历史 | source_changes、plan_baselines | 来源活动 ID、任务、状态/执行者/计划等变更、发生及获取时间；首次纳入时可验证计划基线 | 来源活动按来源 ID 去重；无可靠 ID 时记录依据，不伪造历史；起点前未知过程不补造 |
| 状态语义与计时节点 | status_mappings | 项目/工作流/原始状态 ID、七项语义、独立计时节点标记、修订及恢复验证状态 | 七项语义沿用既定名称；未映射不是第八种语义，暂停受影响判断；不能仅按状态名称识别 |
| 三级规则与公司日历 | rule_overrides、calendar_revisions、calendar_days | 系统/版本/需求作用范围、明确覆盖的配置项、变更原因与来源；工作日、节假日和调休日历 | 按项继承；单一弹窗编辑；删除本层覆盖即可恢复继承；并发阈值只允许系统默认层设置 |
| 需求管理与阶段结果 | requirement_settings、stage_evaluations | 需求量级及子单量级、明确不适用的职能与依据；三个阶段结果、计算依据和最近计算时间 | 基础流程、细节完整按既定职能判断；测试阶段固定包含应处理后代；缺少工单先待确认，不自动完成 |
| 原始反馈与处理结果 | raw_submissions、submission_checks | 来源表和记录 ID、原始业务字段、平台创建人身份、提交时间、读取时间及内容修订；每次校验结果、原因和规则版本 | 按来源表＋记录 ID 唯一识别；同一记录编辑只新增修订，不伪装成新提交；拒绝及待复核记录也保留 |
| 有效反馈历史和当前进度 | effective_feedback、current_progress | 有效原始记录引用、任务、百分比、当前情况及风险说明；每任务当前有效记录引用 | 按平台提交时间选最新有效记录，编辑时间不用于争夺最新；旧链接仍有效；采集标识不作为有效性门槛 |
| 通知及待反馈提醒 | collection_requests、notification_jobs、delivery_attempts | 内部采集请求、任务、接收人、通知类别、应执行时间、计划截止时间、文案版本、中转记录 ID、尝试及结果 | 采集轮次仅用于后台安排和提醒；同任务固定反馈链接；通知业务键唯一；发送资格在执行前复核 |
| 同步和持久任务 | sync_runs、source_events、background_jobs | 同步范围、游标、成功时间、事件 ID、处理阶段、失败及重试、任务执行锁 | 数据处理完成后才推进游标；失败不清空旧数据；重启后从数据库续办；原子领取任务避免并发执行 |
| 管理异常与审计 | exceptions、audit_events | 异常编号、类型、受影响对象、当前状态和恢复证据；操作人、对象、前后差异、原因和时间 | 行动中心与异常页共用记录；事项数与去重工单数分开；恢复验证通过再关闭，审计不删除 |
| 实际日期补录与修正 | actual_time_adjustments | 原值、调整值、管理员、时间、原因和依据、撤销/替代关系 | 仅管理员及所有者可执行；保留原始状态历史，不回写 TB；不靠计划日期填补实际时间 |
| 上线留档和历史修订 | release_archives、archive_revisions、followup_items | 实际上线时冻结的范围、规则/日历版本、计划与实际节点、遗留工单/风险及负责人、漏同步修正记录 | 仅已上线且选入留档版本进入历史查询；后续修正留版本，不用当前状态静默覆盖原留档结果 |

数据量不明的完整附件、聊天内容和无关 TB 字段不默认全部复制；只保存已确认页面、规则和追溯所需的数据。凭证、授权码和完整访问令牌不得进入以上普通数据表。

## 4. 必须保持一致的处理规则

### 4.1 反馈

- 核对任务稳定身份、可见编号、标题、可信提交人、实际执行者、活跃版本/跟踪区间及正式反馈资格。仅有编号和姓名不能通过校验。
- 只采集已确认范围内的核心专业子单；百分比为 0–100 整数，风险或阻塞说明按既定规则校验。100% 反馈不等于工单正式交付完成。
- 同任务允许多次提交。最新有效记录更新当前反馈，错误编号、错误标题和非执行者记录不得覆盖有效进度。历史与拒绝原因保留。
- 对活跃状态、执行者或状态映射的变化，重新检查受影响反馈和后续动作；不能把曾通过只读测试的候选直接当作正式有效反馈。
- 如同一任务出现提交时间完全相同、内容冲突的有效候选，建议标记待复核并保留上次确定值，不依赖抓取顺序随机覆盖。该边界策略为技术建议，进入实现验收前定稿。
- 建议将原始记录留存、校验结果、有效历史、当前值和相关异常/提醒变化放在同一事务边界内；失败不得出现“历史写了、当前值没更新”的半完成状态。

### 4.2 规则、阶段与计时

- 三级配置按项继承，保留每项来源。未设置特殊配置时按已确认原型隐藏详情并说明继承来源；编辑窗口首次展示实际生效值，保存原因和差异。
- 统一语义为：未开始、开发中、测试中、处理中但不计时、暂停、交付完成、非交付终态。开发/测试计时开始结束为独立标记。
- 非交付终态算已处理，不当作实际交付；未知状态、来源缺失、缺少开始时间分别保留未知和异常，不能填零或自动推算。
- 测试阶段覆盖测试总单及缺陷、验收任务及子任务、辅助子单等全部应处理后代。重新打开后按实际规则回退；不等于版本实际上线。
- 并发关注按同一实际执行者在全部活跃版本中的核心专业子单计划区间重叠判断，系统默认阈值 3，不按版本/需求覆盖，不作为绩效结论。
- 日历和归档计算依据可追溯；正常状态变更时间直接作为对应计时依据，明确遗漏时由管理员补录。来源历史不能被补录记录覆盖。需求量级沿用既定例外：按记录当前量级重新分组统计，不保存量级统计快照，不能因留档而冻结该分组口径。

### 4.3 通知与恢复

- 沿用余莉个人发送、AI 表格自动化中转路径。接收人按任务实际执行者或已确认阶段通知规则确定，不新建特殊通知对象页面。
- 任务可见编号、任务名称和计划截止时间同步到中转记录；固定反馈链接由系统预填编号与任务，内部 ID 不展示给填写人。
- 应用执行前再次核对资格、是否已有有效反馈、版本是否仍活跃、是否已处理同一通知。内部轮次不要求填写人输入，不因新轮开始拒绝旧链接反馈。
- “待处理、已交给平台、平台执行成功、明确失败、结果未知”分开。平台执行成功不自动记成收件人确认已读；同一个逻辑通知可以有多次受控尝试，但不能创建重复逻辑通知。
- 结果未知时进入对账或人工核实，不自动重发。重启先读取持久记录及来源结果，不盲目补发关机期间所有通知。
- 只有自身受控通知和前置失败人工修复路径已有证据。跨人员送达、自动获取平台运行结果、超时对账与重试防重仍待补验。

## 5. 登录与权限方案

### 使用方式

建议员工打开内网后台后使用钉钉确认身份，系统核对企业范围、已确认人员映射和后台授权，再建立登录会话。登录失败或身份不明时不降级为匿名访问，也不根据姓名授予权限。

这属于拟定接入方式。钉钉扫码登录/工作台免登哪一种适合当前应用、内网地址能否配置、浏览器如何回到后台、是否需要内部 HTTPS，必须用当前应用实测。既有本机 OAuth 验证脚本不等于正式多用户登录与权限已经实现。没有验证成功前，不把真实公司数据发布到无鉴权原型上。

内网后台仍需访问钉钉、Teambition 和 AI 表格接口；“内网访问”不等于断网可运行。TB 云端不会因后台在公司内网就能直接访问私网回调；首阶段以本机主动读取和对账为优先方案。

### 四档后台权限

| 权限 | 允许 | 禁止或限制 |
| --- | --- | --- |
| 无后台访问权限 | 按已有身份及工单资格接收通知、在 AI 表格反馈 | 不得访问后台业务页面和接口；不能自行取得代填资格 |
| 查看者 | 查看已授权管理范围内的数据 | 不可保存规则、纳入/结束版本、补录时间或管理权限 |
| 系统管理员 | 管理映射、角色、规则、日历、状态语义、版本和异常，补录实际时间 | 不因管理员身份获得权限授予/撤销能力 |
| 系统所有者 | 包含管理员能力，并管理后台权限 | 不得删除、降级、撤销或解除最后一名所有者的有效身份关系 |

版本负责人、需求负责人、执行者和参与者是业务职责，不能代替上述权限。首版不擅自新增按部门隔离、跨企业共享或新的细分权限体系；已有数据可见范围仍须遵循确认规格及来源授权。

### 必须通过的保护检查

- 会话由服务端建立，授权回调须关联本次发起请求，防止别人替换登录结果；浏览器不持有应用密钥。
- 业务接口逐次校验身份和当前权限；退出、撤权、停用及解除身份映射后，旧会话不能继续执行受限操作。
- 写操作校验请求来源及会话，日志不带令牌、密码或完整授权回调参数。
- 首位所有者通过一次性受控初始化绑定已核实人员，不开放“首个访问者自动成为所有者”。初始化及后续授权留审计。
- 最后一名所有者保护必须在数据库事务内检查，覆盖同时撤权、降级和解除映射的并发情况。
- 恢复数据库不能自动公开服务。重新核对权限、凭证有效性和通知处理记录后再启用真实业务。

## 6. 开发任务与验收顺序

以下为本地拆分草案，不是已创建的 GitHub Issue。仓库约定正式任务与规格进入 GitHub Issues；确认后按现有事项复用或拆建，避免重复建单。本轮不发布远端事项，也不修改远端状态。

| 任务 | 范围与依赖 | 必须达到的验收结果 |
| --- | --- | --- |
| P01 交付基线与可重复运行 | 核对已合并 main、总原型 v2、文档增量；建立正式业务库迁移和启动配置 | 干净工作区可复现启动；环境测试库与业务库分开；失败不覆盖已有数据；凭证不入仓库 |
| P02 登录、身份和四档权限 | 依赖 P01；先验证当前钉钉应用的内网登录回路，再实现服务端授权 | 获准人员可登录，未授权人员被拒绝；查看者直接调用写接口仍被拒绝；撤权及时生效；首位与最后一名所有者保护有效 |
| P03 版本纳入和来源绑定 | 依赖 P01/P02；按已确认定义识别版本、类型、分类、职能、父子关系与同步起点 | 测试版本完整纳入，未知状态/缺失结构可定位；来源读失败不清空数据；不修改 TB 工作事实 |
| P04 持久同步与对账 | 依赖 P03；轮询、分页、幂等、来源历史、失败及重启恢复；回调另设接入条件 | 同一记录重复读取不重复建单；失败不丢游标、不当作空数据；重启后能补读；缺失/隐私/删除不混成同一种结果 |
| P05 分层规则与阶段计算 | 依赖 P03/P04；规则、日历、语义、职能不适用确认、计时标记、全局并发阈值 | 三级按项继承及恢复正确；状态未映射暂停受影响计算；阶段完整与回退正确；跨版本并发只用系统阈值 |
| P06 反馈入库和当前值 | 依赖 P02/P04/P05；可信身份、平台时间、原始修订、校验、有效历史及当前值 | 错编号/错标题/非执行者不覆盖有效值；重复读取不重复生效；旧链接可用；记录编辑不改变提交排序；事务失败可恢复 |

### 10.3 资源实测内容

在同一台电脑、相近的日常办公条件下，对比“后台与数据库停止”及“后台与数据库运行”的情况。记录办公软件是否打开、软件版本、数据规模、同步间隔、查询范围、访问人数及测试持续时间，避免把其他软件负载全归到本系统。

覆盖四种场景：日常运行、集中补同步、预计多名用户同时查看、数据库备份。另观察一段运行时间内的内存趋势与任务积压；仅测启动瞬间或空数据库不构成通过。

| 评估对象 | 必须记录 | 如何用于决定 |
| --- | --- | --- |
| 内存 | 后台及数据库进程的内存口径、通常值和峰值；整机可用内存、是否出现持续增长及明显换页 | 进程共享内存不能简单相加当成实际物理占用；结合整机剩余空间和办公流畅度判断，不把缓存配置当总上限 |
| CPU | 后台、数据库和整机的通常及峰值负载；高负载持续时间 | 区分短时峰值与持续占满；判断是否影响日常办公及同步处理 |
| 硬盘 | F 盘数据库/日志/备份大小、增长量、可用空间；集中同步与备份期间读写情况 | 有容量边界和日志轮转；不能用剩余容量充足代替读写性能合格 |
| 使用体验 | 日常办公是否明显卡顿；后台常用页面响应及多人查看时表现 | 使用者可按相同步骤复验；主观体验与测量结果一起报告 |
| 同步与恢复 | 通常同步耗时、断线后积压数量、补齐耗时、失败与重复情况 | 依据实际接口配额及规模判断是否满足业务需要；此前 15 分钟刷新只是讨论目标，不写成已确认保证 |
| 备份 | 执行时长、备份体积、资源峰值、恢复结果及与同步冲突情况 | 确认能备份也能恢复，并评估安排到低负载时段是否足够；同机备份不当作机外灾备 |

测试样本优先采用经授权的代表性测试数据或脱敏构造数据。正式预期版本数、任务数、历史保留和同时使用人数，在评估前依据当前资料核实；缺失的业务量假设列清后一次性向用户确认，不套用旧讨论数字或擅自复制正式数据。持续时间与数值门槛结合该规模在执行方案中确定，未定前不宣称资源合格。

### 10.4 本机方案的决定方式

1. 若日常办公无明显影响、资源留有余量、同步/恢复和备份满足确认目标，建议继续本机小范围试用，同时保留电脑关机就暂停处理的限制。
2. 若占用偏高但问题可局部改善，先限制并行同步和数据库连接、改为增量读取、分批计算或错开备份，验证正确性后只复测受影响场景；不以关闭认证、取消审计、减少必要历史或降低断电数据保护换取低占用。
3. 若优化后仍明显影响办公，或业务要求电脑关机时继续运行，建议暂停扩大试用，评估其他常开设备或受控托管方案。只迁数据库不能解决本机后台停止的问题。
4. 评估结果用用户可理解的报告交付：测试条件、通常/峰值占用、办公影响、补齐耗时、未通过项、优化前后对比、方案建议及可能费用。开发者不能代用户接受明显影响办公或新增费用。

每次评估按第 9 节提供具体人工验收步骤和正确结果；在本批交接文本中保留测试证据、下一次评估节点及部署取舍状态。当前只登记验收与评估计划，没有开始压测、启动服务、迁移数据库或购买云服务。
