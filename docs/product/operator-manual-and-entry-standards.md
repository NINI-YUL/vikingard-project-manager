# Teambition 与钉钉协同项目管理操作手册及填写规范

文档状态：实施前使用基线稿

版本：V1.2

日期：2026-09-29

更新日期：2026-10-31

适用对象：系统所有者、系统管理员、查看者、版本负责人、需求负责人、执行者、测试人员、通知接收人

依据：《Teambition 与钉钉协同项目管理需求策划方案》及已确认的项目决策

> 本手册描述系统按既定方案完成实现后的标准操作。正式上线前，应根据最终页面名称、按钮位置和通知样式补充截图，但不得改变本文已经确认的业务规则。

## 一、使用原则

### 1.1 两个平台分别做什么

| 平台 | 主要用途 | 操作原则 |
|---|---|---|
| Teambition | 创建和维护版本研发工作单，更新标题、结构、负责人、参与者、计划时间和工作状态 | 研发工作的事实以 Teambition 为准 |
| 钉钉协同项目管理 | 查看管理看板、维护管理配置、接收提醒和通知、填写进度反馈、处理数据异常 | 管理信息和反馈历史在钉钉侧维护 |

任何人员都不需要为了使用管理看板，再在钉钉侧手工创建一套重复任务。

### 1.2 四条基本规则

1. 工作单的标题、结构、状态、执行者和计划时间在 Teambition 修改。
2. 进度百分比、当前情况、风险原因和所需协助通过钉钉收集表单反馈。
3. 钉钉侧不自动反向修改 Teambition 工作单。
4. 缺失信息不按零处理，也不根据标题或姓名猜测。

### 1.3 操作人员看到的主要区域

以下是操作人员使用的逻辑区域，不代表最终必须拆成相同数量的物理数据表：

- 行动中心：查看风险、逾期、即将到期和数据待处理事项；
- 对象详情：查看版本、需求、工作单或人员的完整上下文；
- 配置库：维护系统默认、版本覆盖和需求级覆盖；
- 任务主表：查看从 Teambition 同步的工作单当前信息；
- 原始反馈记录：保留表单的全部提交，主要用于校验和审计；
- 有效反馈历史：保留通过校验的每次反馈；
- 异常与审计：处理结构、人员、状态、同步和通知异常。

普通执行者通常只需要使用 Teambition、钉钉通知和进度反馈表单，不需要进入配置库或直接维护反馈历史。

## 二、角色与职责

| 角色 | 主要职责 | 不应执行的操作 |
|---|---|---|
| 系统管理员 | 维护工作日历、状态语义映射、人员映射、人员角色、系统默认规则；处理同步和投递异常；启用或结束版本 | 不根据姓名猜测人员映射；不直接修改原始反馈以制造有效记录 |
| 版本负责人 | 确认版本范围、同步起点、版本级规则覆盖、通知范围和版本结束 | 不为单个需求大量复制版本配置，应使用需求级覆盖记录例外 |
| 需求负责人 | 正确拆分需求和工作单；维护需求级规则、跟进方式、基础/细节完整范围；处理需求异常和风险 | 不通过修改标题规避结构字段；不把任务完成百分比当作正式完成状态 |
| 执行者 | 在 Teambition 维护工作状态；按通知填写当前进度和风险；发现信息错误时及时反馈 | 不修改表单预填的工单 ID和任务标题；不代替他人提交 |
| 测试人员 | 维护测试总单、缺陷和验收过程状态；准确使用测试与缺陷工作流 | 不用缺陷标题代替缺陷分类；不跳过必要的重新打开流程 |
| 参与者/通知接收人 | 接收完成、风险或协调通知；进入详情查看上下文并采取业务行动 | 不将收到通知理解为自动获得工作单执行责任 |

一个人可以同时承担多个业务或管理职责；这些职责不自动授予后台权限。人员业务角色由系统管理员或系统所有者维护，执行者与参与者仍以具体 Teambition 工作单为准。

### 2.1 系统权限与业务职责分开

| 系统权限 | 可执行的操作 | 限制 |
|---|---|---|
| 无后台访问权限 | 按已确认身份、工单关系及采集/通知规则接收消息、提交反馈 | 不能进入本系统后台；不会因此自动取得通知或代填资格 |
| 查看者 | 只读查看管理数据 | 不可修改配置、执行版本管理或补录实际时间 |
| 系统管理员 | 维护人员映射、业务角色、规则、状态语义和日历；处理异常、执行版本管理和实际时间补录 | 不因管理员身份自动取得授予或撤销系统权限的能力 |
| 系统所有者 | 包含系统管理员能力，并可管理系统权限 | 最后一名所有者不可删除、撤权、降级或解除映射 |

版本负责人、需求负责人、执行者、参与者及测试/运营/策划/PM 等业务角色，不自动获得系统管理员或所有者权限。修改后台数据仍须取得相应系统权限；业务角色只参与业务职责和通知条件，不能替代系统授权。只有身份映射已确认的人员可以保留业务角色或系统权限，解除映射时须撤销相关配置并保留审计；最后一名所有者受上述保护。

正式系统的授权、撤权、首位管理员/所有者初始化和权限校验均须留痕；原型只演示会话内配置，不能据此认定正式鉴权已实现。

## 三、各角色日常操作速查

### 3.1 执行者

1. 在 Teambition 打开自己负责的工作单。
2. 开始工作、暂停、返修或完成时，及时更新实际状态。
3. 核心专业子单的计划时间发生变化时，通知需求负责人并更新计划开始和截止时间。
4. 收到钉钉进度采集或逾期提醒后，打开消息中的任务专属表单链接。
5. 确认系统预填的工单 ID和任务标题正确，不要修改。
6. 填写当前进度、当前情况；有风险或阻塞时填写原因及所需协助。
7. 提交后如发现填写错误，重新打开正确链接再提交一次，不修改或删除历史记录。

### 3.2 需求负责人

1. 创建核心需求或优化需求，并按本手册拆分子单。
2. 检查工单类型、父子关系、职能、执行者和计划时间。
3. 确认核心需求的基础流程、细节完整是否使用默认配置，并核对参与者与通知业务角色。
4. 根据工作复杂度确认百分比或里程碑跟进方式。
5. 每日查看行动中心的需求风险、逾期、即将到期和数据异常。
6. 对已拒绝、已取消或无需处理的工作单补充原因，确认其确实不再交付。
7. 工作单重新打开后，确认需求完成节点已经回退，并重新跟进后续完成。

### 3.3 版本负责人

1. 在版本启用前确认版本范围、同步起点和版本级覆盖规则。
2. 查看启用预览中的覆盖数量、受影响对象和待配置问题。
3. 日常按版本筛选查看风险、逾期、即将到期和人员协调事项。
4. 定期检查数据覆盖率，覆盖率不足时优先处理数据问题，再解读指标。
5. 已上线结束前确认实际上线事实，逐项登记未完成工单的后续负责人和处理方式，未完成工单的实际完成时间留空。未解决业务风险逐项登记后续负责人和处理方式；影响上线事实、版本范围或遗留工单清单可信度的数据异常先核实，不能以留存绕过；其他数据异常记录指标影响、负责人和后续处理方式，受影响历史指标记“未知”或“不可计算”，不填零。缺少可核对清单时不得当作没有遗留或异常。
6. 退出管理后确认停止日常同步、采集和通知，并按处理方式保留记录：已上线且选入留档的版本进入历史查询；未上线终止保留完结记录；误选停止纳入保留停止纳入记录，不进入完结版本或已上线历史统计。移除与恢复纳入的条件见第十一章。

### 3.4 系统管理员

1. 每日优先进入“数据待处理”检查新增异常。
2. 在“异常与审计”的待处理页按状态未映射、人员待匹配、字段缺失或结构问题、同步失败和投递失败五类检查；职能或必要计划时间缺失等源字段由需求负责人回 Teambition 修正。
3. 维护节假日、调休和特殊工作日。
4. 审核系统默认或版本级配置变更，检查影响范围并保留变更记录。
5. 确认人员离职、转岗或账号变化后，及时更新人员映射和人员角色。
6. 连续同步失败达到 15 分钟时介入；恢复后核对当前数据并检查对账结果。

## 四、Teambition 工单结构规范

### 4.1 标准层级

```text
版本
├─ 核心需求
│  ├─ 核心专业子单
│  ├─ 辅助子单
│  ├─ 测试总单
│  │  └─ 缺陷单
│  └─ 验收总单
│     └─ 验收任务单
└─ 优化需求总单
   └─ 优化需求
      └─ 优化任务单（可选）
```

### 4.2 各类工作单填写要求

“必填”表示缺失会造成结构、同步、统计或通知异常；“按需”表示业务需要时填写；“可缺”表示缺失不构成数据异常。

| 业务对象 | 工单类型 | 父级 | 职能 | 执行者 | 计划时间 | 关键要求 |
|---|---|---|---|---|---|---|
| 核心需求 | 需求 | 所属版本范围 | 不填写 | 明确负责人 | 建议填写 | 一个需求只属于一个版本；参与者应覆盖相关协作人员 |
| 核心专业子单 | 子需求 | 核心需求 | 必填 | 必填 | 必填 | 职能从 UI、美术、动效、数值、客户端、服务端、KGUI、后台中选择；同一职能允许多个子单 |
| 辅助子单 | 任务 | 核心需求 | 不要求 | 按需明确 | 可缺 | 礼包、模块开关、红点、系统引导、压测、兼容方案、音效等使用此类 |
| 测试总单 | 测试任务 | 核心需求 | 不要求 | 明确负责人 | 可缺 | 汇总该需求的测试工作；不使用“返修”表示缺陷修复 |
| 缺陷单 | 缺陷 | 测试总单 | 不要求 | 明确处理人 | 可缺 | 记录具体问题；通过缺陷状态反映修复和各环境验收过程 |
| 验收总单 | 任务 | 核心需求 | 不要求 | 按需明确 | 可缺 | 必须设置“工单分类=验收总单” |
| 验收任务单 | 任务 | 验收总单 | 不要求 | 明确负责人 | 可缺 | 系统优先按父级识别；不要直接挂在核心需求下冒充验收任务 |
| 优化需求总单 | 优化需求总单 | 所属版本范围 | 不填写 | 按需明确 | 可缺 | 一个版本使用一个汇总容器；自身不计入优化需求完成率 |
| 优化需求 | 优化需求 | 优化需求总单 | 可缺 | 无子单时必填 | 可缺 | 单一职能可直接执行；需要多人拆分时再创建优化任务单 |
| 优化任务单 | 任务 | 优化需求 | 可缺 | 必填 | 可缺 | 职能可填数值、客户端、服务端、动效、UI，也允许为空 |

### 4.3 工单标题规范

标题应直接表达“交付对象 + 具体工作”，让不打开详情的人也能判断在做什么。

推荐格式：

```text
[对象/模块] 具体交付内容
```

推荐示例：

- `[联盟礼包] 完成礼包购买与领取流程`
- `[战斗结算] 接入客户端结算界面`
- `[新手引导] 修复第三步无法继续的问题`
- `[预约活动] 完成预发布环境验收`

不推荐示例：

- `处理一下`
- `程序任务`
- `礼包相关`
- `问题修改`
- `开发中-客户端-某某需求`

不要把工单类型、职能、执行者或状态长期写在标题中。这些信息必须填写在结构化字段里，标题变更也不应被用来改变工单角色。

### 4.4 父子关系规范

- 核心专业子单、辅助子单、测试总单和验收总单直接挂在核心需求下。
- 缺陷单挂在对应测试总单下。
- 验收任务单挂在验收总单下。
- 优化需求挂在本版本的优化需求总单下。
- 优化任务单挂在对应优化需求下。
- 不要仅靠标题中的“测试”“验收”“客户端”等文字表达父子关系。
- 工作单移动到其他需求或项目后，检查版本归属、通知对象和配置是否仍适用。

### 4.5 职能填写规范

- 核心专业子单必须填写职能。
- 同一核心需求可以存在多个相同职能的核心专业子单。
- 礼包、模块开关等辅助子单不填写职能，不属于数据异常。
- 优化需求和优化任务单允许不填写职能。
- 缺少核心专业子单职能时，不在标题中猜测，工作单进入待配置。

### 4.6 执行者与参与者规范

- 执行者是对单个工作单交付负责的人，应尽量保持唯一且明确。
- 参与者是需要协作、知情或接收通知的人，不等于执行者。
- 核心专业子单没有执行者时，系统暂停向该工作单发送进度采集，并产生数据异常。
- 不要为了让某人收到通知而把其设置为执行者，应将其加入相关需求参与者，并核对对应业务角色；当前不提供特殊通知对象配置入口。
- 人员转岗或离职后，需求负责人处理工作单归属，系统管理员处理钉钉人员映射和人员角色。

### 4.7 计划时间规范

- 核心专业子单必须填写计划开始时间和截止时间。
- 计划时间应反映当前可执行计划，发生正式调整后及时更新。
- 同一天开始并完成按一个工作日计算。
- 核心专业子单缺少任一计划时间时，显示“周期未配置”，不猜测周期，并进入数据异常。
- 优化需求总单、优化需求、优化任务单、其他任务和缺陷单允许缺少计划时间；缺失时不参与截止提醒、逾期风险和依赖时间的指标。
- 缺陷即使填写计划时间，也不进入常规进度采集或核心专业子单开发历时统计。

### 4.8 描述和备注规范

工作单描述至少应让接手人理解以下内容：

1. 目标：完成后解决什么问题；
2. 范围：本工作单包含什么、不包含什么；
3. 完成条件：怎样算完成；
4. 依赖：依赖的人员、资源或前置工作；
5. 关联资料：设计稿、文档、接口说明或验收标准。

缺陷单还应补充：出现环境、复现步骤、实际结果、预期结果和必要附件。不得在工单中填写账号密码、应用 Secret、Token等敏感信息。

### 4.9 需求量级填写规范

系统可以根据计划工作日提出量级建议：

| 量级 | 默认建议范围 |
|---|---|
| 小型 | 不超过 5 个计划工作日 |
| 中型 | 6–10 个计划工作日 |
| 大型 | 11–20 个计划工作日 |
| 特大型 | 超过 20 个计划工作日 |

- 量级是管理分类，不等于人员工时，也不直接决定优先级。
- 需求负责人可以根据实际复杂度调整系统建议。
- 修改核心需求量级时，当前核心专业子单随之更新；之后仍允许单个子单独立调整。
- 历史统计按记录的当前量级重新分组，不保留量级统计快照，因此调整后历史报表分组可能变化。

### 4.10 工单类型、工单分类和内容分类

- 工单类型用于识别需求、子需求、测试任务、缺陷、优化需求总单、优化需求和任务等结构角色。
- 工单分类用于标记“验收总单”等共用同一工单类型的特殊角色。
- 内容分类用于描述任务内容，不用于判断核心需求或优化需求。
- 三者不能互相替代，也不要通过修改标题代替结构化分类。

## 五、工作流状态填写规范

### 5.1 通用原则

- 状态必须反映真实工作阶段，不为“让报表好看”提前完成。
- 进入暂停或挂起时，应在备注中说明原因和恢复条件。
- 进入已拒绝、已取消、无法复现或重复缺陷等非交付终态时，应填写判断原因。
- 工作恢复后使用重新打开或相应非终态，不新建重复工单代替原工单。
- 终态工作单重新打开后，上级需求的相关完成节点会回退，并开启新的状态周期。

### 5.2 各类工作流使用方法

#### 核心需求、优化需求和优化需求总单

使用精简的需求汇总状态：待处理、进行中、暂停、已完成、已拒绝、已取消。

- 顶层“已完成”表示负责人确认该需求整体结束，但不替代系统对子单的完成判断。
- 顶层“已拒绝”或“已取消”表示结构收口，但不计入实际交付。
- 优化需求有直接子单时，以全部直接子单进入终态判断完成；没有子单时，以优化需求自身状态判断。

#### 核心专业子单

主要使用：待处理、开发中、暂停、返修、已完成、已拒绝。

- 开始实际制作时进入“开发中”。
- 暂时停止且暂停期间不应计入开发历时时进入“暂停”。
- 已交付后因问题需要继续处理时进入“返修”。
- 专业工作交付结束时进入“已完成”。该类工作单不承担独立测试和验收流程。
- 确认不执行时进入“已拒绝”，并填写原因。

#### 通用任务和优化任务单

根据实际过程使用：待处理、进行中、开发完成、测试中、测试完成、已完成，并按需使用暂停、返修、已拒绝或已取消。

- “开发完成”表示开发处理完毕、等待测试，不属于最终完成。
- “测试中”表示已进入实际测试阶段。
- “测试完成”表示本轮测试已经结束；如工作单仍有收尾流程，再进入“已完成”。
- 不经过测试的普通任务可按正式工作流允许的路径直接完成。

#### 测试总单

使用：待处理、测试中、暂停、测试完成、已拒绝、已取消。

- 测试发现问题时创建缺陷单，不把测试总单改成“返修”。
- 测试总单进入“测试完成”但仍有未终态缺陷时，不满足核心需求“测试阶段完成”。

#### 缺陷单

标准主路径为：

```text
待处理 → 修复中 → 已修复 → 测试中
→ 内网验收通过 / 预发布验收通过 / 线上验收通过
→ 已关闭
```

- 根据实际发布范围跳过不适用的验收阶段。
- 测试失败时进入“重新打开”，随后回到“修复中”。修复后再次进入“测试中”会开始新的测试轮次。
- “挂起”用于确认暂时不能继续处理的缺陷。
- “无法复现”“重复缺陷”“已拒绝”属于非交付终态，应记录原因。
- 三个验收通过状态是过程状态，不是最终关闭状态。

### 5.3 开发历时与测试历时注意事项

- 正常进入开发中或测试中的状态时间直接作为对应计时起点，按公司工作日累计，不要求逐条人工核实状态日期。
- 开发完成停止开发计时，测试完成停止本轮测试计时；后续等待验收或发布不计入测试历时，两者均不等于最终交付或版本实际上线。
- 缺少开始记录时显示“未知/不可计算”，不能填零或用计划时间推算；由系统管理员补录或修正实际时间，保留原记录、调整值、操作人、时间、原因和依据，不反向修改 Teambition 历史。
- 验证失败后再次进入测试中开启新的测试轮次，旧轮次继续保留。
- 暂停或挂起期间不累计。
- 未进入测试中就直接选择测试完成或验收通过，会产生“测试开始时间缺失”异常。
- 缺陷在内网、预发布和线上验收通过时分别记录阶段检查点；验收通过状态之间的流转不延长已结束测试轮次的历时，也不自动新开轮次。验证失败后重新进入测试中，才开启新轮次，原轮次和检查点继续保留。
- 历时仅用于计划和复盘，不用于评价个人效率。

### 5.4 补录或修正实际时间（REQ-07）

1. 从需求中的工单抽屉点击“打开完整工单详情”，在“实际时间”区域点击“补录 / 修正时间”。仅系统管理员和系统所有者可操作；原型使用管理员演示身份。
2. 在统一弹窗选择开发或测试，以及对应轮次；核对原始记录与当前生效时间，再填写调整后的实际日期。可以只补一端；无法确认的日期保持空白，空白表示未知，不能拿计划时间代替。
3. 填写变更原因和补录依据。切换阶段/轮次会保留输入；保存前核对本次修改轮次清单。日期必须有效，不能晚于当天；两端都有值时，结束日期不能早于开始日期。
4. 点击“保存实际时间”。保存后标注“人工补录”，可在工作单动态和“查看完整历史”中查看调整前后值、原始记录、原因、依据和操作人/时间；完整历史新增“时间修正”类型和“人工补录”来源筛选。
5. 取消或 Escape 不保存。原型只演示当前会话变化；受影响历时显示“待重新计算（演示）”，不修改 Teambition 历史或工单完成状态，也不重算其他看板。正式系统须按生效工作日历及计时规则计算。

## 六、钉钉进度反馈表单填写规范

### 6.1 谁需要填写

常规进度采集只覆盖：

- 活跃版本内；
- 未进入终态；
- 已有执行者且身份映射已确认；
- 属于核心专业子单。

优化需求、优化任务、测试、缺陷、验收和辅助子单默认不进入常规进度采集。

### 6.2 如何打开正确表单

1. 从系统发送的钉钉通知中打开任务专属链接。
2. 每个链接对应一个 Teambition 工作单；不要收藏后长期用于其他任务。
3. 页面打开后，先核对 `TB工单id` 和 `任务` 是否与通知一致。
4. 如果标题或工单 ID不正确，关闭页面并从最新通知重新进入，不要手工改成自己认为正确的值。

### 6.3 字段填写要求

| 字段 | 填写人 | 规范 |
|---|---|---|
| TB工单id | 系统预填 | 不修改。系统以此关联 Teambition 工作单 |
| 任务 | 系统预填 | 不修改。提交时会与 Teambition 当前标题再次校验 |
| 当前进度百分比 | 执行者填写 | 填写 0–100 的整数，表示当前范围内已完成工作的判断，不是已消耗时间比例 |
| 当前情况 | 执行者填写 | 明确选择或填写“正常”“有风险”或“已阻塞”，并与实际情况一致 |
| 风险原因与所需协助 | 执行者填写 | 正常时可留空；有风险或已阻塞时必填，说明原因、影响和需要谁提供什么协助 |

表单不要求填写版本，也不要求再次填写预计完成日期。版本由 Teambition 关联关系识别，计划日期仍在 Teambition 维护。

### 6.4 进度百分比的判断方法

- `0%`：尚未开始实际工作；
- `1%–99%`：根据已经完成且可确认的工作范围填写实际判断；
- `100%`：执行者认为本工作单约定范围已经完成。

百分比应基于完成范围，不按“工期已经过半所以填 50%”计算。`100%` 也不会自动把 Teambition 工作单改成已完成，执行者仍需在 Teambition 更新正式状态。

### 6.5 当前情况的填写方法

| 当前情况 | 使用条件 | 风险说明 |
|---|---|---|
| 正常 | 按当前计划可以继续推进，没有已知事项影响目标 | 可留空；如有一般说明可简要补充 |
| 有风险 | 尚可推进，但存在可能影响质量、范围或时间的事项 | 必须说明风险、可能影响和希望获得的协助 |
| 已阻塞 | 当前不能继续推进，必须等待外部条件或决策 | 必须说明阻塞原因、依赖对象、所需动作和期望解决时间 |

推荐的风险说明结构：

```text
问题：缺少预发布环境的服务器配置。
影响：客户端联调无法继续，可能影响本周五提测。
需要协助：请服务端负责人在周三 15:00 前补齐配置并通知联调。
```

不合格示例：

- `有问题`
- `等别人`
- `可能做不完`
- `暂无`

### 6.6 提交和纠错

- 同一任务允许多次提交，每次都会保留历史。
- 系统只使用通过校验的提交；当前反馈取最新一条有效记录。
- 填错后重新提交正确内容，不删除或覆盖之前的记录。
- 如果修改了预填工单 ID或任务标题，提交可能保留在原始反馈记录中，但不会进入有效反馈历史。
- 非当前执行者或无反馈资格人员代填时，提交不会进入有效反馈历史。
- Teambition 标题已经变化时，应使用系统重新生成的最新链接。

### 6.7 里程碑跟进

采用里程碑跟进的核心专业子单应设置 3–5 个带计划完成日期的节点。执行者反馈当前里程碑、里程碑状态和当前情况；首次进入“进行中”时记录节点开始时间。

里程碑反馈的最终表单字段和界面仍需在反馈体验原型中确认。正式上线前，应在本节补充最终页面截图和逐字段说明；未确认前不得要求执行者自行在备注中拼接里程碑结构。

## 七、行动中心与看板使用规范

### 7.1 默认入口

系统默认进入行动中心，优先展示需要采取行动的事项，而不是展示人员排名或综合健康分。

行动中心包含两个页签：

- 风险与到期；
- 数据待处理。

### 7.2 风险与到期

顶部指标卡包括：高风险需求、需关注需求、风险工单、已逾期工单、三日内到期。

页面主要区域：

- 风险关注：只展示核心需求下存在风险的核心专业子单；
- 已逾期工单：按需求聚合展示已经逾期且未终态的核心专业子单；
- 即将到期工单：按公司工作日历展示未来三个工作日内到期的核心专业子单；
- 风险责任人：按风险核心专业子单的实际执行者汇总协调信号。

风险责任人区域只用于帮助管理者找到需要协调的人，不形成工作量排名、效率评分或绩效结论。

### 7.3 筛选规则

- 默认查看全部活跃版本。
- 版本筛选作用于两个页签的全部区域。
- 职能筛选可以多选，作用于风险、逾期、即将到期和风险责任人。
- 数据待处理不受职能筛选影响，避免隐藏系统性问题。
- 筛选后没有匹配工作单的需求整组隐藏。

### 7.4 数据覆盖率

数据覆盖率必须与业务指标一起查看：

- 不低于 90%：正常；
- 70% 至 90%：数据不完整；
- 低于 70%：指标暂不可靠。

覆盖率不足时，应先查看缺失原因和允许排除项，不把缺失值当作零进度，也不据此得出人员或需求表现结论。

### 7.5 对象详情

版本、需求、工作单和人员详情保留面包屑与对象上下文，但各自显示的指标和侧栏不同，不应认为每一页都有同一组风险、异常、覆盖率和最近变化：

- 版本详情展示核心需求进展、当前未解决管理信号及重要变化；
- 需求详情展示需求总览、工单时间线和其他直属工作单；
- 工作单详情展示状态、有效反馈进度、执行信息和工作单动态；
- 人员详情展示当前承担的核心专业子单与本人最近变化，不单设“当前管理信号”。

需求详情包括需求总览、工单时间线和其他直属工作单。点击工单可打开详情抽屉，并可继续打开 Teambition 完整工单。

### 7.6 人员详情

1. 从左侧“人员”进入人员详情，按职能分组查找人员；点击姓名切换右侧详情。人员列表可以向左收起并重新展开，不按工作量、风险或逾期数量对人员排名。
2. 顶部四张卡仅显示“在手核心子单”“并发关注”“已逾期”“三日内到期”的名称和数量；并发关注仅提示复核计划重叠，不代表超载或绩效。
3. “来自 N 个核心需求”按当前在手核心专业子单涉及的不同核心需求去重；人员数据只按其实际执行的核心专业子单统计，不把仅参与的工作单归给此人。
4. 下方工单列表展示工作单、所属需求、版本、计划时间、当前状态和进度。Teambition 状态与有效反馈进度分开阅读；百分比反馈显示百分比，里程碑反馈显示里程碑状态，无适用进度时不填造百分比。
5. 计划时间红字表示已逾期，绿字表示按公司工作日历未来三个工作日内到期，正常黑字表示其他情况；已逾期工作单不重复计入三日内到期。颜色只标示到期关系，不表示工作单状态或人员表现。
6. 右侧最近变化只记录与该人员有关的重要变化；人员页不单设管理信号区。需要更早记录时使用“查看完整历史”入口，历史查询按已确认的版本复盘页面查看，不与当前行动队列混用。

### 7.7 历史查询与版本复盘

1. 历史查询只查看当前选入留档且已确认实际上线的版本。热更版本可不纳入；管理员调整留档范围时必须填写原因并保留操作记录，页面明确“按当前选择的留档版本统计”。
2. 页面按“版本总览 → 版本详情 → 需求详情”下钻。版本总览显示版本数、版本周期中位数、按时上线版本和核心需求按时完成率；中位数同时显示工作日和自然日，工作日为主值，并标明可计算样本数。缺少可信日期的版本不进入对应指标分母。
3. 版本详情查看计划开始时间、计划上线时间、实际上线时间、版本周期和完整核心需求列表。版本周期同时显示自然日和工作日，首尾日期均计入；工作日采用版本实际上线时生效的工作日历。
4. 需求详情查看需求周期、开发阶段周期、测试阶段周期、计划完成时间、实际完成时间、按日甘特时间线和原始工作单明细。八类核心专业子单纳入开发阶段，测试与验收分开；辅助子单不纳入开发阶段周期但影响需求最终交付。
5. 首次计划基线是版本正式纳入管理时确认的计划。正式改期不能覆盖基线；录入纠错、上线前漏同步的完成事实可以由管理员依据证据修正并留下审计。实际上线后才完成或重开只记录为后续变化。
6. 延期原因由显式授权的系统管理员（通常为 PM）登记确认，填写原因类型、影响环节、说明和证据。系统不从日期差自动推断责任，也不生成个人评分。历史详情无可信完成时间时保持空值，不补造日期。

### 7.8 人力参与度看板

1. 年度堆叠条按年份和当前职能查看所有映射已确认且有效人员的开发、调优、空闲工作日。只读阶段天数，不读作个人出勤、实际投入工时、效率或绩效；年度条不显示工单数量。当前年标题下同时显示全年工作日和截至统计截点已发生的工作日，已完成年份只显示全年工作日。
2. 月度甘特时间带按周、日期展示每人的连续主阶段，左侧为姓名、当前职能及当月三类阶段工作日。非工作日在星期下方标“休”，特殊工作日以区别底色表示并参与工作日数；今天线只标当前演示截点。月度页不提供本月完成工单合计或单张工作单详情。
3. 开发期表示人员仍关联至少一个核心专业子单开发中的核心需求；无开发期而关联需求仍待测试、相关缺陷或适用验收完成时为调优期；没有这类进行中关联需求时为空闲期。空闲期仍可能处理优化、辅助或缺陷等其他工作单；一天同时涉及多个需求时按开发优先于调优判定。
4. 月度阶段条中的“共N张”指整个已结束连续阶段完成的工单数，“ING N张”指进行中阶段截至统计截点已完成的工单数。阶段跨月、跨年时各片段重复显示同一个整段数，不能相加成月度或年度工单总量；完成计数归属完成时有效的处理人或测试人，拒绝、取消、纯容器和未完成工单不计入。
5. 资料不完整时显示未知，未来日期留白；两者不计为空闲。正式产品允许通过“显示全部人员”辨认离职或映射未确认等非默认人员状态；当前原型仅演示离职人员，不能用其他人员的缺失记录推断空闲。原型采用固定演示数据；处理人/测试人字段及其历史仍须租户验证后才能用于真实看板。

## 八、配置库操作规范

从统一主导航点击“配置库”进入配置工作台，点击“返回行动中心”返回。底部不再提供 A/B/C 方案选择，也不使用左右方向键切换方案；现有各页操作保持不变。

### 8.1 配置优先级

```text
系统默认 → 版本覆盖 → 需求级覆盖
```

下层只记录例外。没有设置下层值时，继续继承上层；不要为了“看起来完整”把同一配置复制到每个版本和需求。

### 8.2 修改配置前

1. 确认当前生效值和来源层级。
2. 确认修改是系统规则、版本例外还是单个需求例外。
3. 查看预计影响对象和当前覆盖数量。
4. 明确修改原因。
5. 重要修改应由对应负责人复核；规则设置采用保存前复核、填写原因后直接保存，不另走草稿发布流程。

配置库顶部不提供通用“保存草稿／演示发布／影响预览”。版本操作在对应弹窗确认；规则、工作日历、人员配置及状态映射在各自编辑窗口保存，仍须完成窗口内既有的影响复核、原因及校验；状态映射保存后继续等待恢复验证。通用变更记录及规则页记录保留，通知对象页只读。

### 8.3 修改配置后

- 检查生效值及来源层级是否正确；
- 检查受影响需求和工作单是否符合预期；
- 保留变更人、变更时间、前后值和原因；
- 例外结束后使用“恢复继承”，不要手工复制上层值覆盖。

### 8.4 主要配置项

- 工作日历；
- 进度采集时间点（星期与时分；常规对象仍限定为满足身份与状态条件的核心专业子单）；
- 百分比/里程碑跟进建议阈值；
- 基础流程和细节完整职能范围；
- 通知节点与接收规则展示、人员角色（暂不增加特殊通知对象配置入口）；
- 需求量级；
- 开发关注阈值：默认 3 张，仅系统默认层级可编辑；版本和需求只读。跨全部活跃版本按同一实际执行者的核心专业子单计划区间重叠数判断，只提示管理复核，不代表超载或绩效。业务风险阈值沿用原有口径，本页未新增编辑项；
- 状态语义映射；
- 人员映射；
- 版本同步起点和启用状态。

### 8.5 工作日历

- 默认周一至周五为工作日，节假日、调休日和特殊工作日由系统管理员维护。
- 安排周末集体加班时，将对应日期配置为“特殊工作日”，并填写加班说明；该日期按 1 个工作日参与计划周期、逾期、三日内到期、开发历时和测试历时计算。
- 工作日是日期级计算单位，不代表人员实际投入小时；首版不录入半天或小时级加班。
- 修改工作日历前查看影响范围，修改后复核受影响版本、需求和工作单的当前计算结果，并保留变更人、时间、前后值和原因。

### 8.6 状态语义映射

1. 从“配置库 → 状态语义 → 状态映射”进入，先选择 Teambition 项目和工作流，再逐行核对原始状态名称、状态 ID、统一管理语义、计时节点和映射结果。
2. 点击统一的“编辑映射”按钮，在一个弹窗内维护全部状态；七项可选语义为未开始、开发中、测试中、处理中，但不计时、暂停、交付完成、非交付终态。“未映射”是配置异常，不是第八项语义。
3. 独立维护开发计时开始、开发计时结束、测试计时开始、测试计时结束四类计时节点；开发完成和测试完成只结束对应计时，不代表最终交付。
4. 保存前必须填写变更原因；允许先保存部分映射，未映射状态继续保留。原始状态 ID、名称和历史始终保留，不通过改名覆盖来源状态。
5. 保存后显示“待验证恢复”；相关重新同步、计算或校验确认受影响能力已恢复后才关闭对应异常，不能以保存成功代替恢复成功。未映射工作单仍同步，但受影响的完成判断、开发/测试历时、风险和通知暂停。

本节对应原型基线 STATUS-01；原型只演示当前会话内的编辑、保存反馈和审计，不执行真实同步、重算、通知或异常关闭。实际时间缺失或错误的补录规范见 5.3。

#### 影响与恢复（STATUS-02）

- 保存状态映射后切换到“影响与恢复”，核对关联异常、受影响能力及剩余未映射状态；当前结果应为“待验证恢复”。
- 原型可点击“模拟验证失败”查看失败说明及异常保留，再复核重试；只有补齐当前工作流剩余映射后才可点击“模拟验证成功”。这些操作不执行真实同步、计算或通知。
- 成功后显示“已恢复（模拟）”，EX-101 移出待处理列表，发现和历次操作继续保留在审计中；其他异常不变。重新保存映射后，原验证失效，须再次验证。
- 正式系统仍须以相关重新同步、计算或校验确认能力恢复为准，不能以原型模拟结果关闭真实异常。

### 8.7 人员映射

- 只有系统管理员或系统所有者可以确认人员映射。
- 手机号或邮箱完全一致只能生成待确认建议。
- 仅姓名相同或近似时不得自动匹配。
- 人员确认前，其工作单继续同步，但系统不得向候选人发送消息。

## 九、提醒与通知处理规范

### 9.1 进度采集和待反馈提醒

- 默认按公司时区（初始北京时间）每周二、周四 10:00 发起，支持配置多个“星期 + 时分”；系统、版本和需求层级按配置项继承或覆盖时间点，不扩展常规采集的工单类型。
- 仅当配置时间点命中且当天为公司工作日才执行。调休上班日和特殊工作日也须命中所选星期及时间；休息日跳过，不自动补发。
- 常规采集只覆盖活跃版本中未进入终态、有执行者且身份映射已确认的核心专业子单；执行者或映射缺失时进入异常处理，不猜测接收人。
- 首次采集不计入提醒次数。
- 一个工作日后仍未收到有效反馈时，提醒执行者一次。
- 再过一个工作日仍无有效反馈时，通知系统管理员，并停止本轮继续提醒执行者。
- 工作单进入终态或收到有效反馈后，取消本轮尚未发送的提醒。
- 上一轮采集尚未结束时，不重复创建新的采集轮次。

### 9.2 截止和逾期提醒

- 核心专业子单在截止前第二个工作日提醒一次。
- 逾期后的首个工作日发送第一次催办，之后默认每隔两个工作日提醒一次。
- 提交有效进度后，当前逾期催办停止并重新计时；再过两个工作日仍未终态时恢复。
- 常规进度采集与逾期催办重合时合并处理，避免同一事项重复通知。
- 工作单进入终态后，取消尚未发送的截止或逾期提醒。

### 9.3 完成通知

| 通知节点 | 判断条件 | 默认接收人 | 操作注意 |
|---|---|---|---|
| 基础流程完成 | 按配置职能逐项核对：对应核心专业子单全部处理完成，缺少工单的职能须由负责人明确确认不适用 | 核心需求参与者中角色为测试、运营、策划或 PM 的人员 | 不能只核对已有工单而忽略缺失职能；未知状态、数据缺失不视为完成 |
| 细节完整完成 | 累计基础流程和额外配置职能全部满足处理完成条件；额外职能缺少工单时同样须确认不适用 | 核心需求参与者中角色为测试、运营、策划或 PM 的人员 | 不能只看额外职能的现有工单；基础流程未满足时，不判定细节完整完成 |
| 优化需求完成 | 有子单时全部直接子单终态；无子单时优化需求自身终态 | 参与者中角色为策划的人员 | 优化需求总单只汇总，不发送单条完成通知 |

完成门槛中存在已拒绝、已取消或无需处理等非交付终态时，通知仍可发出，但必须单独显示非交付终态数量，不能把这些工作单计入实际交付。

规则设置页使用“基础流程阶段 → 细节完整阶段 → 测试阶段”的节点名称。细节完整须累计基础流程和额外职能；测试阶段固定检查全部应处理后代，暂不新增完成通知，也不代表实际已上线。规则编辑与继承方式以原型基线 RULE-01 为准。

### 9.4 重新打开和通知更正

- 已通知完成的节点发生工作单重新打开时，系统向原通知对象发送一次状态更正。
- 再次完成后可以重新发送完成通知。
- 同一需求、同一通知节点、同一状态周期只发送一次，避免重复通知。

## 十、常见异常处理

| 异常 | 可能原因 | 处理人 | 标准处理 |
|---|---|---|---|
| 工作单未出现在看板 | 不在活跃版本、启用时当前快照未补齐、同步延迟或结构无法识别 | 需求负责人/管理员 | 先核对版本、工单 ID和结构，再查看同步异常；不要重复创建工单 |
| 核心专业子单显示待配置 | 缺少职能、执行者、计划时间或父级错误 | 需求负责人 | 回到 Teambition 补齐结构化字段 |
| 状态无法计算 | 新状态或状态映射缺失 | 系统管理员 | 在状态语义映射中确认语义；修复前不手工填结果 |
| 无法发送进度通知 | 执行者未设置、人员未匹配或投递失败 | 需求负责人/管理员 | 先修正执行者，再确认人员映射和投递记录 |
| 表单校验失败 | 工单 ID或标题被修改、标题已更新、填写人不符合资格 | 执行者/需求负责人 | 使用最新通知中的正确链接重新提交 |
| 提交后当前反馈未更新 | 提交尚未处理或校验失败 | 管理员 | 查看原始反馈的校验结果，不直接修改有效历史 |
| 进度 100% 但需求未完成 | Teambition 工作单未终态，或仍有其他未终态后代 | 执行者/需求负责人 | 更新真实工作状态并检查其他工作单 |
| 已完成后需求又回退 | 纳入门槛的工作单被重新打开或新增非终态工作单 | 需求负责人 | 确认重新打开是否正确，继续按新状态周期跟进 |
| 指标明显偏低 | 数据覆盖率不足 | 管理员/负责人 | 先处理缺失数据，不把缺失值当零 |
| 工作单重复 | 人工重复创建或错误补录 | 需求负责人/管理员 | 保留正确 Teambition 工单 ID，按审计规则处理重复数据，不直接批量删除 |

“待处理异常”只列未解决且影响数据、计算、反馈或通知的事项，按问题类型分组；高风险、阻塞和逾期在行动中心“风险与到期”处理，允许为空的字段不算异常。配置状态或人员映射后，继续核对相关数据重新同步、计算或校验的恢复结果；同步或投递失败重试成功后，才从待处理项移出。审计记录按时间倒序保留失败、重试、确认、成功及配置发布等过程，与待处理项通过异常编号关联；无变化同步不占管理待办。原型暂不提供异常详情抽屉或审计筛选，不执行真实重试。

## 十一、版本启用、移除与结束管理清单

### 11.1 启用前

- [ ] 已确认版本负责人；
- [ ] 已确认版本中的核心需求和优化需求总单；
- [ ] 已设置同步起点；
- [ ] 已检查工单结构和类型；
- [ ] 已检查核心专业子单的职能、执行者和计划时间；
- [ ] 已确认状态语义映射；
- [ ] 已确认人员映射和人员角色；
- [ ] 已检查基础流程、细节完整和通知对象；
- [ ] 已检查工作日历；
- [ ] 已查看预计同步范围和待配置数量。

### 11.2 结束管理前

先在“结束管理”弹窗中选择符合实际情况的处理方式，不为退出管理填写不真实的上线或终止结果。

**已上线并结束**：

- [ ] 已由版本负责人确认向目标用户实际上线，并记录实际上线日期；
- [ ] 已取得可核对的未完成工单清单，逐张明确后续负责人和处理方式；缺项不可确认结束，未完成工单的实际完成时间保持空白；
- [ ] 未解决业务风险逐项明确后续负责人和处理方式并保留记录；
- [ ] 影响上线事实、版本范围或未完成工单清单可信度的数据异常已先核实；不得以“明确保留”绕过；
- [ ] 其他数据异常已逐项记录指标影响、负责人和后续处理方式；受影响历史指标标为“未知”或“不可计算”，不填零；
- [ ] 缺少可核对的风险、异常或未完成工单清单时，未将“未知”当作零而放行；
- [ ] 已明确是否选入历史留档；仅实际上线且选入留档的版本进入已上线历史统计。

**未上线，终止管理**：

- [ ] 已确认版本未实际上线而停止开发，并记录终止原因及遗留事项处理；
- [ ] 不填写实际上线日期；保留完结记录，不进入已上线历史指标。

**误选，停止纳入**：

- [ ] 已确认属于误选且已经产生管理数据；记录误选原因；
- [ ] 保留已采集事实、反馈、通知和审计，不宣称版本已上线或已停止开发；
- [ ] 退出日常管理，保留在停止纳入记录中，不进入完结版本或已上线历史统计；
- [ ] 不自动回到普通候选列表；需要再次纳入时按 11.4 显式恢复。

以上方式均须确认停止常规同步、进度采集和通知，并保留对应历史事实及操作记录。

### 11.3 移除误选版本

- 仅尚未产生任何同步、反馈或通知数据的误选版本可“移除”；只要存在任一管理数据即不可移除。
- 填写移除原因并确认后，只撤销本系统的纳入关系，不删除 Teambition 版本；操作记录保留，版本重新进入选择版本列表。
- 再次选择按启用流程核对范围并确定同步起点；启用时仍须补齐当前工单快照，不因尚可移除而省略首次同步。

### 11.4 恢复纳入

1. 系统管理员或系统所有者从“停止纳入记录”中显式发起恢复。
2. 重新核对当前版本负责人、工单结构与字段、状态、范围、规则及待配置问题，确认新的跟踪起点；不直接跳过复核恢复采集或通知。
3. 保留旧事实和停止记录，按工单 ID 延续当前数据，不重复创建或计数；中断期间标明资料不完整，不补造过程、状态历史或历时。
4. 恢复纳入不等于首次启用，不将停止记录删除或自动当作新的普通候选。

原型的快照复核摘要及“模拟首次同步/恢复同步”仅为会话演示，不代表真实 Teambition 快照核对或生产同步已经完成。

## 十四、常见问题

### 14.1 我可以直接在钉钉任务主表中改标题或状态吗？

不可以。标题、状态、父子关系、工单类型、执行者和计划时间以 Teambition 为准，应回到 Teambition 修改。

### 14.2 表单中的工单 ID和任务标题可以编辑，能改吗？

不要修改。它们只是产品能力上无法锁定，但系统提交后会重新校验。修改后可能只保留为无效原始记录，不会更新当前反馈。

### 14.3 填错进度怎么办？

使用同一任务的正确链接重新提交。系统保留历史，并以最新一条有效记录作为当前反馈。

### 14.4 为什么填了 100%，任务还没有完成？

百分比是执行者反馈，不是 Teambition 正式状态。请在工作确实结束后，按对应工作流更新 Teambition 状态。

### 14.5 为什么已拒绝的子单仍然不阻塞完成通知？

已拒绝属于非交付终态，说明该工作已经收口但没有交付。系统仍可判断结构完成，但会在看板和通知中单独显示非交付终态数量，不把它计入实际交付。

### 14.6 为什么我没有收到通知？

先检查自己是执行者还是参与者，以及对应通知是否按人员角色发送。若人员映射未确认或投递失败，系统会进入数据待处理，由管理员处理，不会自动猜测替代收件人。

### 14.7 缺陷单需要填写计划时间吗？

不强制。缺失不会产生数据异常，也不进入依赖计划时间的提醒和历时统计；缺陷仍参与状态统计和核心需求测试阶段完成判断。

### 14.8 为什么数据覆盖率低时不展示完整结论？

因为缺失数据不能按零计算。覆盖率低于 70% 时，指标可能无法代表实际情况，应先处理数据问题。

### 14.9 可以直接在钉钉任务主表新建一条任务吗？

普通操作人员不应这样做。没有 Teambition 工单 ID的纯手工记录不会进入自动同步。确需补录时，只能由系统管理员或系统所有者创建，并在取得正确 Teambition 工单后显式绑定。

### 14.10 可以把工作单设为“仅参与者可见”吗？

业务确有需要时可以使用，但首版钉钉侧展示不会继承 Teambition 的参与者级可见范围。系统会保留来源可见范围标记，但一般任务不建议无必要设置为隐私任务；涉及敏感内容时，应先确认钉钉侧可见范围是否满足要求。
