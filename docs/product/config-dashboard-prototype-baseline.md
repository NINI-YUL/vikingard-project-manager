# 配置库与管理看板原型基线

日期：2026-10-15

对应 Issue：#13

状态：行动中心、需求详情、工作单详情、版本详情、人员详情、异常与审计页、历史查询页及人力参与度独立原型已阶段确认；配置库其余页面继续评审

范围：只记录产品原型与交互口径，不作为正式后台实现规格

## 1. 原型资产

- 统一原型入口：`docs/prototypes/config-dashboard-prototype.html`；默认方案 A 左侧“历史查询”进入已合并的三页历史复盘。
- 独立历史复盘评审源文件：`docs/prototypes/history-review-three-level-prototype.html`；统一入口内含其已确认的自包含演示内容，打开统一原型不依赖此文件。
- 人力参与度原型：方案 A 左侧“人力参与度”进入年度与月度两视图；`docs/prototypes/personnel-participation-prototype.html` 保留为独立评审源文件，统一 HTML 内含其演示内容，无需依赖该文件即可打开。
- 启动命令：`node scripts/serve-product-prototype.mjs`
- 方案切换：`?variant=A`、`?variant=B`、`?variant=C`
- 原型为只读、内存态演示，不连接 Teambition 或钉钉，不包含持久化、鉴权或正式后台服务。
- 版本范围页仅允许误选且尚无同步、反馈或通知数据的版本填写原因后“移除”，并重新进入选择列表。有任一管理数据则禁用移除；若属误选，在“结束管理”弹窗内选择“误选，停止纳入”，保留已采集事实和原因，不进入完结版本或已上线历史，也不冒充版本终止开发。恢复纳入由管理员从停止纳入记录显式发起，复核当前快照、负责人、范围及规则，并确认新跟踪起点；保留旧记录、按工单 ID 延续，标记中断期资料不完整，不重复计数或推算缺失历时。停止纳入的版本不自动回到普通候选列表。原型复核输入和模拟恢复同步并非真实 TB 验证。新启用版本的“待首次同步”与“模拟首次同步”仅用于展示限制，正式启用仍应补齐当时的当前工单快照。
- 已上线结束允许存在未完成工单，但须先由版本负责人确认实际上线，并对每张遗留单分别确认后续负责人及处理方式；缺一项即不能确认。未完成的实际完成时间始终保持空白。原型仅对有演示明细的版本展示逐项确认；其他版本的未知明细不等于零，不能在原型中据此确认上线结束。
- 已上线结束时，未解决业务风险逐项明确后续负责人和处理方式并留存；影响上线事实、版本范围或遗留工单清单可信度的异常先核实，不能以留存代替。其他异常须逐项记录指标影响、负责人和处理方式；受影响历史指标标记“未知”或“不可计算”，不填零。缺少可核对风险/异常清单不得按无异常放行。原型的核实依据与确认均为人工演示输入，不是 TB 实时校验；独立历史看板仍为固定演示数据，不随版本范围内存操作重算。

## 2. 行动中心基线

### AC-01 页面结构

- 保留“风险与到期”和“数据待处理”两个页签。
- “风险与到期”采用左右布局：左侧为“风险关注”和“已逾期工单”，右侧为“即将到期工单”和“风险责任人”。
- 所有区域在同一页面从上到下展开。

### AC-02 指标卡

顶部保留五张指标卡：高风险需求、需关注需求、风险工单、已逾期工单、三日内到期。

指标随版本筛选和职能筛选更新；指标只反映当前筛选范围，不产生健康度、排名或评分。

### AC-03 风险关注

- 标题为“风险关注”。
- 风险等级只使用高风险、需关注、正常；正常作为层级/图例，不展开风险工单。
- 风险矩阵的工单字段拆分为“状态”和“进度”。
- 只展示核心需求下的核心专业子单。
- 风险原因与所需协助保留在工单行中。

### AC-04 已逾期工单

- 标题为“已逾期工单”。
- 使用按需求聚合的横向分布样式，并保留核心专业子单明细。
- 只展示截止时间已过且尚未进入终态的核心专业子单。

### AC-05 即将到期工单

- 标题为“即将到期工单”。
- 使用按日期/工作日为轴的纵向时间线，而不是按需求作为时间线分组。
- 时间节点按今天、1 个工作日后、2 个工作日后、3 个工作日后排列。
- 工单卡片中保留所属需求、执行者、状态/进度和截止信息。
- 三日内按公司工作日历计算。

### AC-06 风险责任人

- 按风险核心专业子单的实际执行者汇总。
- 展示风险、逾期、三日内到期等协调信号。
- 不按参与者汇总，不生成排名、评分或绩效结论。

### AC-07 筛选作用范围

- 默认范围为全部活跃版本。
- 版本筛选作用于两个页签全部区域。
- 职能筛选支持多选并包含“全部”。
- 职能筛选作用于风险关注、已逾期工单、即将到期工单和风险责任人。
- 数据待处理页签不受职能筛选影响。
- 筛选后仍显示匹配工单所属需求；无匹配工单的需求整组隐藏。

### AC-08 数据待处理

- 保留“字段缺失或配置错误”和“待人工确认”两个区域。
- 按问题类型分组。
- 数据覆盖率展示可计算记录数 / 应统计记录数、缺失原因和允许排除项。

## 3. 需求详情基线

### REQ-01 页面结构

保留需求总览、工单时间线、其他直属工作单；删除“全部工单”区域。

### REQ-02 工单时间线

- 展示 UI、美术、动效、数值、客户端、服务端、KGUI、后台核心专业子单，以及测试总单。
- 工单名称后显示开始时间和截止时间。
- 缺少计划时间的工单进入“未排期”。
- 点击工单打开右侧详情抽屉，抽屉保留“打开完整工单详情”。
- 使用按日展开的日期网格，并在表头按周分组；每张工单以横向状态条表示开始、截止和当前状态。
- 周末、节假日和特殊工作日使用不同底色；工作日数以当前生效工作日历计算。
- 时间线过宽时允许横向滚动，左侧职能、工单名称和起止信息保持可见。
- 日期行不显示“演示基准”文字；原型参考线只用于样式评审，不属于正式产品字段。
- 已确认的视觉版式：沿用总原型的页面灰底；时间轴使用轻量表格边框、按周/日清晰分组和浅色状态条，完成、进行中、未开始及阻塞/风险同时保留文字标识。只调整呈现，不变更工单字段、日期与工作日计算口径、横向滚动或点击工单打开详情的交互。

### REQ-03 其他直属工作单

- 展示核心需求直属、未进入时间线的辅助子单、验收总单等工作单。
- 不展示子任务的子任务。
- 验收总单可汇总验收任务数量、未完成数量和风险数量。
- 已确认的视觉版式：其他直属工作单采用浅边框、少量状态强调的紧凑卡片；保留原有名称、职能、状态、执行者、计划时间、进度和下属工单摘要。只调整呈现，不变更展示范围、统计口径或点击卡片打开详情的交互。

### REQ-04 需求总览

- 不展示“结构完成率”或由终态数量换算的百分比。
- 保留终态工作单数量作为事实数据，不将其解释为实际交付比例。

### REQ-05 完整工作单详情

- 顶部四张信息卡固定为：执行者、计划时间、当前状态、当前进度。
- 当前进度按跟进方式展示：百分比跟进显示最新有效反馈百分比；里程碑跟进显示当前里程碑名称和状态；测试总单、验收总单和辅助子单显示“进度不适用”。
- 当前进度下显示进度更新时间，取最新一条有效进度反馈的提交时间；普通同步和状态变化不更新时间；无有效反馈时显示“待反馈 / 暂无有效反馈”。
- 执行信息展示跟进方式、本轮开发开始时间、本轮开发历时、累计开发历时和重新打开次数；重新打开次数保留为页面字段。
- 本轮开发历时只计算当前开发周期；累计开发历时为所有开发周期之和。明确映射为暂停的状态不计入开发历时；工作日按生效工作日历计算。
- 本轮开始时间来自 Teambition 状态历史中首次进入“开发中”语义的时间；完成后重新打开并再次进入“开发中”时开始新一轮；进度反馈、计划开始时间和普通同步不改变本轮开始时间。
- 工作单动态合并进度反馈、状态变化、配置变化和实际时间修正，显示时间、类型、来源、内容、记录人和有效性，默认显示最近 10 条。
- 右侧只展示当前仍未解决且直接影响工作单的管理信号；删除重复的“最近变化”区域。
- “查看完整历史”支持按日期、类型和来源筛选；校验失败的原始反馈只在异常与审计中查看。
- “查看有效配置”打开只读抽屉，展示直接影响工作单的生效值及来源；修改统一进入配置库或对应需求配置。
- “在 Teambition 中查看”直接打开原工作单；来源不存在或用户无权限时禁用并提示原因。
- 下属任务只显示总数、未完成数量和适用的类型汇总，不展示风险数量，也不在详情页展开任务列表。

### REQ-06 通知接收人预览

- 核心需求详情提供只读入口，按适用的通知节点列出符合接收条件的人员、接收规则及来源，并说明未纳入原因；优化需求节点在核心需求中标为不适用。
- 预览只用于需求范围核对，不在此处修改身份、业务角色或系统权限，也不表示通知已经发送。原型的参与关系、渠道状态和默认规则来源均为显式演示数据；人员映射和业务角色取当前会话配置，不代表真实 Teambition 参与关系、钉钉投递能力或版本/需求覆盖已核验。

### REQ-07 实际时间补录与修正（2026-10-30 确认）

- 工作单完整详情增加“实际时间”区域，按开发、测试及轮次展示生效开始/结束日期与来源。“补录 / 修正时间”入口只对系统管理员和系统所有者展示；业务角色不产生编辑资格，保存时再次检查系统权限。原型使用明确标注的管理员演示身份，不代表正式鉴权。
- 一个统一弹窗选择阶段和对应轮次，同时显示原始记录、当前生效时间、调整后日期；原因及依据必填。切换阶段或轮次保留输入，保存前明确列出本次所有修改轮次，取消或 Escape 放弃本次未保存修改。
- 允许仅补一端日期；留空表示未知，不能用计划时间补造实际时间。填写的实际日期须有效且不晚于当天；两端均有值时结束日期不能早于开始日期。校验失败不写入任何轮次。
- 保存后仅更新当前工作单及指定轮次的会话生效值，标记“人工补录”；原始状态日期、原始历史和其他工作单/轮次不覆盖，也不因此将工单判为完成。
- 保留原始值、调整前后值、阶段/轮次、原因、依据、操作人和操作时间；工作单动态与完整历史展示“时间修正 / 人工补录”，完整历史可按此筛选。配置审计保留操作摘要。
- 原型按北京时间以日期粒度演示，不推导实际投入工时；受影响的本轮/累计开发历时显示“待重新计算（演示）”，不继续冒用旧演示值。其他固定看板及历史指标不实时重算，不修改 Teambition 状态或历史；正式系统按已确认的工作日历、暂停及计时节点规则重新计算。
- 日期及轮次是显式演示数据；正式系统须使用可信工单身份与实际状态历史，不能从演示轮次或计划日期推断历史。

## 4. 明确不做

- 不增加整体健康度、排名、人员评分或绩效评价。
- 暂不增加版本或风险的历史趋势；人力参与度的年度/月度阶段时间带作为单独已确认视图。
- 不把测试总单、缺陷单、验收总单、验收任务单和辅助子单放入行动中心三个交付清单。
- 不开始正式后台开发，不直接提升原型代码为生产代码。

## 5. 版本页确认补充

### VER-01 同页版本列表

- 活跃版本列表与版本详情在同一页面展示。
- 左侧显示活跃版本号和风险需求数量，右侧显示当前版本详情。
- 左侧版本列表默认展开，可向左收起；收起状态仅在当前使用过程中保留，刷新或重新进入后恢复展开。
- 点击左侧版本后，右侧详情同步切换；结束版本从活跃列表移除并进入历史查询。

### VER-02 当前管理信号

- 按高风险、阻塞、已逾期、数据或配置问题排序。
- 首屏最多显示 5 条，超过时提供“查看全部”，并带入当前版本筛选进入行动中心。
- 没有信号时显示“当前版本暂无需要处理的管理信号”。

### VER-03 无活跃版本

- 当前版本结束后，自动切换到配置顺序中的第一个活跃版本。
- 没有其他活跃版本时，左侧显示“暂无活跃版本”，右侧隐藏指标卡、需求列表、管理信号和最近变化。
- 系统管理员显示“前往配置库启用版本”；普通用户显示“当前暂无活跃版本”。
- 已结束版本通过“历史查询”查看。

### VER-04 系统管理员判定

- 管理员由已验证钉钉 `userId` 与显式系统权限角色判定。
- Teambition 项目管理员、版本负责人、需求负责人、执行者、参与者和人员业务角色不自动获得系统管理员权限。

## 6. 人员详情基线

### PER-01 人员列表与切换

- 保留应用左侧主导航；人员详情内另设左侧人员列表，按职能分组，点击姓名切换右侧完整详情。
- 人员条目显示姓名和逾期核心专业子单数量，不按工作量、风险或逾期数排列人员名次。
- 人员列表可向左收起为窄栏，并可重新展开；收起或切换人员时不丢失当前详情。窄屏可将列表改为横向排列，不改变分组关系。

### PER-02 顶部指标

- 只展示“在手核心子单”“并发关注”“已逾期”“三日内到期”四张卡的名称和数量，不显示卡片底部说明。
- 并发关注、已逾期和三日内到期仅用数字字体颜色区分，不使用整条数字底色。
- 在手核心子单指该人员作为实际执行者、尚未进入终态的核心专业子单；所涉核心需求数按不同核心需求去重，文案为“来自 N 个核心需求”。
- 并发关注是计划区间重叠达到阈值后的复核信号，不代表实际同时投入、超载或个人绩效。
- 已逾期与三日内到期按生效工作日历和工作单截止时间分别统计；已逾期工单不重复计入三日内到期。

### PER-03 当前承担的核心专业子单

- 明细展示：工作单、所属需求、版本、计划时间、当前状态、进度。顶部数量应与同一人员实际执行的明细口径一致，不将仅参与的工作单归给此人。
- 工作单状态取 Teambition 状态，与进度分列；百分比跟进显示有效反馈百分比，里程碑跟进显示里程碑状态，没有适用进度时不捏造百分比。
- 计划时间按到期关系着色：已逾期为红字，未来三个工作日内到期为绿字，其他情况为正常黑字；颜色不改变状态或进度含义。
- 顶部逾期卡只展示数量，具体逾期工作单在明细中查看，不在卡片中逐一堆叠名称。

### PER-04 最近变化

- 人员详情不设独立“当前管理信号”区域；右侧保留“最近变化”，默认最多展示五条与本人有关的重要变化。
- 可记录本人所执行工单的逾期、有效反馈、新增或调整、计划时间变化，以及人员映射和消息投递状态变化；普通无变化同步不作为重要变化。
- 保留“查看完整历史”入口，进入已确认的历史查询复盘页面；不展示评分、排名或绩效变化。

### PER-05 演示数据边界

- 原型的人名、日期、数字和具体工单仅用于视觉与交互评审，不作为真实人员统计或固定业务阈值。正式统计必须由同一执行者的核心专业子单集合计算，不能混入他人的工作单、辅助子单或已终态工单作为在手数量。

## 7. 异常与审计基线

### EX-01 页面结构与分组

- 页面分为“待处理异常”和“审计记录”两个页签；待处理异常按问题类型分组，审计记录按时间倒序展示，不按类型分组，暂不增加筛选。
- 待处理异常包括状态未映射、人员待匹配、字段缺失或结构问题、同步失败、投递失败五组；字段缺失或结构问题组可包含必需职能缺失、必要计划时间缺失等具体问题。每条展示异常编号与具体类型、对象、当前影响、发现时间、负责处理方和下一步入口。
- 异常编号关联当前问题与其发现、重试、确认、修复等审计事件；审计记录可包含已解决历史及配置发布，不代表当前待办数量。原型的六条待处理项和七条审计事件仅为演示数据。

### EX-02 收录边界与移出规则

- 待处理异常是尚未解决、需要继续处理且影响数据、计算、反馈或通知的问题。高风险、阻塞、逾期等业务交付问题留在行动中心“风险与到期”；规则允许为空的字段不生成异常，普通无变化同步不占管理待办。
- 状态或人员映射配置完成并不立即关闭异常；只有相关重新同步、计算或校验流程完成并确认受影响能力已恢复后，才从待处理列表移出。同步失败或通知投递失败重试成功后同样移出待处理列表；失败、重试和成功的过程继续保留在审计记录中。
- 待处理列表保留既有处理入口；暂不通过异常编号打开详情抽屉。原型不执行真实配置、同步、重试或投递。

## 8. 数据与计算边界

可直接同步的事实包括标题、状态、父子结构、工单类型、职能、执行者、参与者和计划时间。风险等级、逾期、三日内到期和风险责任人汇总依赖状态语义映射、计划时间、工作日历、人员映射和有效反馈。缺失数据不按零值处理，也不解释为低进度。

### CAL-01 工作日历

- 默认周一至周五为工作日，系统管理员可配置节假日、调休日和特殊工作日。
- 周末集体加班可以配置为特殊工作日，并按 1 个工作日参与计划周期、逾期、三日内到期、开发历时和测试历时计算。
- 工作日是日期级计算单位，不代表人员实际投入小时；首版不记录半天或小时级加班。
- 工作日历变化后，依赖工作日的当前指标按最新生效日历重新计算，并保留配置变更记录。
- 工作日历原型采用左侧月历、右侧本月特殊日期和默认工作周的布局。月历可切换月份并按日期打开编辑弹窗，特殊日期列表只列显式覆盖的日期，默认周末仍不计入。原型的保存、恢复默认和审计提示仅作用于当前会话；正式系统须在修改前展示具体受影响对象，不能将演示输入视为真实重算或修改历史留档口径。

### RULE-01 规则设置页（2026-10-29 确认）

- 页面包含三个模块：配置层级、进度判断配置、进度采集与风险配置；层级显示系统默认、版本、需求。系统默认不显示对象选择；版本显示版本下拉框；需求同时显示版本及该版本下需求的下拉框。
- 系统默认始终展示第二、三模块。版本或需求没有特殊配置时隐藏这两个模块，准确提示“继承系统配置”或“继承版本配置”，提供查看上层配置入口；保存特殊配置后展示当前生效值及逐项来源。
- 一个编辑按钮打开统一弹窗；首次以当前实际生效值预填，再次打开以当前已保存配置预填。只保存修改的配置项，其余继续继承；系统变化不覆盖下层显式配置。可按项使用上层值，或经影响确认恢复当前对象全部继承。
- 基础流程与细节完整分别选择职能，同一职能不得重复；细节完整完成须累计基础流程和额外配置职能。测试阶段只读，固定检查全部应处理后代，包括核心专业、测试及缺陷、验收总单及子任务、辅助子单及其他后代，不允许排除类型；完成不是实际上线。
- 已取消、已拒绝、无需处理等非交付终态不阻塞阶段收口，单列且不计实际交付；每个所选职能缺少对应工单时须由负责人确认不适用，不能自动完成。未知状态、数据缺失不能作完成处理。
- 采集支持多个“星期 + 时分”，默认周二、周四 10:00。使用公司时区，初始北京时间；仅命中时间点且当天为公司工作日才执行，调休和特殊工作日同样适用，非工作日不自动补发。对象保持未进入终态、有执行者的核心专业子单；缺少执行者或映射时走异常处理。
- 开发关注阈值默认 3 张，仅系统默认层级可编辑，版本及需求只读。跨全部活跃版本按同一实际执行者的核心专业子单计划区间重叠计数；只提示复核，不是超载或绩效判断。
- 保存前展示影响范围并填写变更原因；保存即关闭弹窗、更新展示，不另走草稿发布。取消不保存，未保存修改关闭前有放弃确认；保留操作者、时间、原因及前后值和来源的会话记录。
- 基础流程和细节完整完成均通知核心需求参与者中的测试、运营、策划、PM 业务角色；系统权限不产生通知资格。测试阶段暂不新增完成通知。重新打开时向原接收人更正，再次完成按新状态周期通知；不因修改规则补发历史消息。
- 暂不增加特殊通知对象配置入口。当前编辑器只维护规则的会话演示值，不执行真实调度、完成计算、负责人不适用确认、通知或持久化；其余页面的统计及历史演示数据不随规则编辑实时重算。现有业务风险判断口径继续保留，本页未新增可编辑的风险判定阈值。

界面文案使用清楚的中文，不添加纯装饰或重复的英文标题、解释；保留 Teambition、ID 等必要名称和标识。

## 9. 变更控制

后续原型调整应引用基线编号（例如“只调整 PER-03 人员工作单列表”），并说明是否影响展示字段、筛选范围、统计口径或下钻交互。已确认页面的后续变化通过变更记录增量更新；尚未确认的页面继续逐项评审。

## 10. 权限边界补充

- 管理员状态不由原型前端推断；正式系统通过已验证的钉钉 `userId` 与显式系统权限角色判断。
- 被授予“系统管理员”或“系统所有者”系统权限角色的用户，才能看到“前往配置库启用版本”等管理入口。
- Teambition 项目管理员、版本负责人、需求负责人、执行者、参与者和测试/运营/策划等人员角色，不自动获得系统管理员权限。
- 系统权限角色与人员角色分离；授权、撤权和首位管理员初始化均需保留审计记录。
- 系统权限固定为“无后台访问权限、查看者、系统管理员、系统所有者”四档。查看者只读管理数据；系统管理员维护配置、异常与版本管理；系统所有者可管理系统权限并包含系统管理员能力。最后一名系统所有者不可删除、撤权或降级；所有者保护不由业务角色或 Teambition 身份推定。
- 「人员与通知」原型仅保留“人员与权限”和“通知对象”两个页签。“人员与权限”使用一人一行的列表，固定展示姓名、钉钉映射状态、业务角色、系统权限和编辑/删除操作；仅未映射等关键状态使用轻量强调。列表可按姓名或 Teambition ID 搜索，并按未映射、管理员与所有者筛选；窄内容区改为逐人纵向字段。编辑从操作列打开弹窗，集中维护身份映射、业务角色和四档系统权限；表单切换选项时保留已填写原因，缺失原因或候选身份未人工核对时在相应字段附近提示并阻止保存。未映射时不能保留角色、权限或作为通知投递对象；变更生成当前会话审计记录。删除先经确认弹窗，仅移除本系统人员配置，不删除 Teambition/钉钉账号或已同步工作事实；最后一名系统所有者不可删除、降级或解除映射。“通知对象”只引用身份映射、业务角色和参与者关系，不提供授权入口。
- “通知对象”页收敛为通知节点与接收规则两列；移除当前人员选择、逐人演示判断和“当前人员解析”，保留投递条件说明。具体收件人须在对应需求范围核对；当前通用规则页不推算收件人数，需求级只读演示入口见 REQ-06。

## 11. 历史查询复盘基线

### HIST-01 页面结构与范围

- 历史查询采用三层下钻：版本总览 → 版本详情 → 需求详情。
- 只展示当前选入留档且已确认实际上线的版本；未选入的热更版本不进入历史总览指标。纳入或取消纳入由有权限的管理员操作，必须记录操作人、时间和原因；取消纳入不删除已留存事实。
- 版本总览不默认展示全部版本，按当前选择的留档范围统计，并提供版本详情下钻。

### HIST-02 版本总览

- 页面标题为“版本历史数据”。
- 顶部展示已留档并上线版本数、版本周期中位数、按时上线版本和核心需求按时完成率；中位数分别按可计算版本的工作日周期与自然日周期求取，偶数样本取中间两个值的平均，大字显示工作日、底部小字显示自然日，并标注可计算样本数；无可计算版本时显示“—”。
- 版本周期为版本计划开始日至实际上线日，首尾日期均计入；自然日与工作日同时展示，工作日使用该版本实际上线时生效的工作日历。
- 版本按时比较使用首次确认的计划上线时间；实际上线不晚于基线为按时，晚于基线才计算延期工作日。缺少可信计划或实际上线时间的版本保留在列表但不进入相应指标分母，不判定为按时或延期。

### HIST-03 版本详情

- 顶部展示版本周期（工作日大字、自然日小字）、计划开始时间、计划上线时间和实际上线时间。
- 核心需求全部以纵向行列表展示，不限制为 1–4 项；每行对齐展示需求名称、开发周期、测试周期、计划完成时间、实际完成时间、结果及延期原因摘要，点击进入需求详情。
- 版本复盘口径以需求列表外的小字说明呈现，说明计划基线、实际上线确认、工作日历和漏同步修正规则，不再占用独立卡片。

### HIST-04 需求详情与时间线

- 顶部展示需求周期、开发阶段周期、测试阶段周期、计划完成时间和实际完成时间。
- 时间线采用按周分组、按日展开的甘特样式；左侧为环节名称，计划使用灰色基线条，实际按资产类、生产类、测试和验收使用不同颜色，超出计划区间使用斜纹；计划完成和实际完成使用竖线标识，周末/非工作日和特殊工作日使用不同底色，支持横向滚动。
- 开发阶段纳入 UI、美术、动效、数值、客户端、服务端、KGUI、后台八类核心专业子单；辅助子单不纳入开发阶段周期，但仍影响需求最终交付完成。测试周期止于测试完成，验收单独作为后续节点；需求实际完成以全部应交付内容及适用验收完成为准。
- 原始工作单明细使用标题上方、表格下方说明的单卡片平铺样式，六列为环节、类型、计划起止、实际起止、实际时长、较计划；列内容左对齐，说明放在表格下方，实际时长按工作日计算。

### HIST-05 基线、修正与复盘

- 版本正式纳入管理时确认首次计划基线；后续正式改期记录前后值、原因、操作人和时间，不覆盖首次基线。录入纠错经确认后可修正比较基线，同时保留旧值和审计。
- 实际完成取实际上线前最后一次有效完成；上线前漏同步的完成事实经证据核实后可修正历史结果并重算指标，保留首次记录、修正结果、证据、修正人、时间和指标变化。实际上线后才完成或重开的事项不回写上线时结果，列为后续变化。
- 历史计算固定使用版本实际上线时生效的工作日历；后续日历变化不改写旧版本数字。
- 延期原因由显式授权的系统管理员（通常为 PM）登记并确认，记录原因类型、影响环节、说明和证据；系统不从日期差自动推断责任，不生成个人评分。
- 有证据且经授权确认的人工补录可进入指标，并标注人工补录、证据和确认时间；无证据或待确认补录只作为说明，不进入指标。完成时间无法确认时保持空值，不补造日期。
- 本页不展示按需求量级分组的历史分布统计；若未来增加该类报表，继续沿用需求量级按当前记录重算的既有规则，与本页固定交付事实的口径分开。

## 12. 人力参与度看板原型基线

### PART-01 视图与人员范围

- 独立原型包含“年度堆叠条 / 月度甘特时间带”两个视图，可切换年份、月份，并按人员当前职能筛选；默认列出配置库中身份映射已确认且状态有效的全部人员，不以当年是否有核心需求工单作为展示门槛。
- 产品口径允许通过“显示全部人员”查看离职、映射未确认等非默认人员并标明原因；当前原型只演示离职人员，不代表未映射候选人已接入。无法证明的日期不得当作空闲，仅有系统管理员权限不自动建立核心需求参与关系。
- 同一人的阶段跨已纳入管理范围的核心需求汇总，不按版本重复列人；热更是否纳入沿用留档范围，不生成人员排名、评分或“高负荷人数”。

### PART-02 人员参与阶段

- 人员从首次被明确记录为某核心需求下的实际处理人或测试人起建立关联；明确移出该需求或需求正式结束后解除。纯参与者、通知接收人不自动计入。一个人每天只显示一个主阶段。
- 开发期：该人员仍关联的任一核心需求有应交付的核心专业子单处于开发中。没有开发期、但关联需求的应交付核心专业子单已完成，而测试总单、相关缺陷或适用验收尚未完成时为调优期；不再将测试、验收、返修拆成多种颜色。
- 无处于开发或调优中的关联核心需求时为空闲期；优化、辅助或缺陷等其他工单仍可能在处理中或完成。多需求同日按开发期优先、调优期其次、空闲期最后判定；历史资料不足为未知，未来日期留白。经确认无需交付的非交付终态核心专业子单不阻止转入调优期，但不计入交付完成工单数。
- 调优期结束以测试总单、相关缺陷和适用验收完成为准，不要求辅助子单完成；这与核心需求“测试阶段完成”的正式结束条件不同。

### PART-03 年度堆叠条

- 按公司工作日历统计每个人在所选年份的开发、调优和空闲工作日数，12 个月依次展示；节假日与周末不计入，配置的特殊工作日计入。未知和未来不作为空闲，也不计入三类阶段天数。
- 年度条不显示工单数量。行末三项上方只显示数字，下方标“开发天 / 调优天 / 空闲天”。
- 标题下显示“全年工作日 N 天”；当前年份额外显示截至看板统计截点的“当前已工作 N 天”，已完成年份只显示全年工作日。这里的“已工作”是日历工作日，不是个人出勤或实际投入。

### PART-04 月度甘特时间带

- 选择月份后按周表头和逐日日期轴展示各人的连续参与阶段。姓名与当前职能同一行，下一行显示当月开发、调优、空闲工作日数；周末和节假日在星期下方标“休”，特殊工作日采用区别底色且不标“休”。当前演示日的竖线贯穿月度表格，未来日期不分配阶段。
- 同一人主状态连续相同时构成一段，即使中间更换核心需求也不断段；调优或空闲打断后重新进入开发则是新段。每段只计一次整段完成工单数：已结束标“共N张”，进行中标“ING N张”。
- 阶段跨月或跨年时，各月份可见片段重复展示完整阶段的同一个 N，不代表每月各完成 N 张，不能跨片段相加；年度阶段天数仍严格限于所选年份。月度页不设“本月工单合计”，也不展示工单详情或分类清单。

### PART-05 完成工单计数与数据边界

- 所有类型的实际工作单均可计入阶段数量，包括核心专业、优化、辅助、测试、缺陷、验收等；只计有可信处理记录且真正进入交付完成态的工作单，不重复计纯容器总单，不计拒绝、取消等非交付终态。
- 工单按最后一次有效完成时点计入该人员所属的连续阶段，归于完成时有效的处理人或测试人；人员交接前的处理历史可用于阶段关联，但不让前任分享最终完成数。未完成工单暂不计入，重新打开后依据最后一次有效完成重新判断。空闲段可以有完成的非核心需求工单，不改变阶段颜色。

### STATUS-01 状态语义映射页（2026-10-30 确认）

- 页面入口位于“配置库 → 状态语义 → 状态映射”。顶部先选择 Teambition 项目和工作流；表格逐行展示原始状态名称、原始状态 ID、统一管理语义、计时节点和映射结果。
- 统一管理语义固定提供七项：未开始、开发中、测试中、处理中，但不计时、暂停、交付完成、非交付终态。“未映射”表示配置异常，不作为第八项语义。
- 计时节点作为原始状态的独立标记，可选择开发计时开始、开发计时结束、测试计时开始、测试计时结束；开发完成和测试完成只影响计时，不等于最终交付。
- 使用一个“编辑映射”按钮打开统一编辑弹窗，一次维护全部状态；保存前必须填写变更原因。保存后保留原始状态 ID、名称和历史，并显示“待验证恢复”，不直接宣称异常已恢复。
- 允许先保存部分映射；未映射状态继续同步工作单，但暂停受影响的阶段完成判断、开发/测试历时、风险和通知，直到重新同步、计算或校验确认恢复。未知或缺少开始记录的历时显示“未知/不可计算”，不填零。
- 原型仅演示当前会话内的编辑、保存反馈和审计记录，不连接 Teambition，不执行真实同步、重算、通知或异常关闭。

### STATUS-02 影响与恢复页（2026-10-30 确认）

- 与状态映射页共用当前项目、工作流的映射及验证状态；保存映射后显示“待验证恢复”，不再使用旧的“映射已发布”判断。
- 展示关联异常 EX-101、演示影响范围、受影响能力、剩余未映射状态名称和 ID。未映射状态继续同步，受影响的完成判断、开发/测试历时、风险和通知继续暂停。
- 提供明确标注的“模拟验证成功”和“模拟验证失败”操作；保存后才可验证，存在未映射状态时禁止判定恢复成功。失败时保留异常与失败说明，可复核后重试。
- 模拟验证成功后显示“已恢复（模拟）”，仅将对应 EX-101 移出当前待处理列表；其他异常不变。发现、保存、失败与成功的过程在审计中保留；重新保存映射使旧验证结果失效并重新进入待验证恢复。
- 本页及异常列表的联动仅在当前会话演示，不执行真实同步、重算、投递或生产异常关闭；演示影响数量不是实时统计。
