## 1. 给使用者的说明

建议先在用户本机运行后台和数据库，进行受控、小范围内网试用；公网访问暂缓。工单工作事实仍在 Teambition 中维护，进度通过钉钉 AI 表格填写。后台负责校验、计算、显示、权限、通知安排和审计。

当前阶段接受本机依赖：电脑关机、休眠、断网或应用停止时，后台页面、同步、反馈处理及新的通知安排会暂停。AI 表格仍可独立接收表单提交；已经交给钉钉平台的自动化可能继续运行，因此不能把本机停止等同于所有平台消息已取消。恢复后读取未处理提交、对账任务当前值，先核实再处理通知，不补造历史、不盲目补发。后续需要全天候可用时，再迁移到长期在线的托管环境，另核费用及维护安排。

## 3. 最小部署结构

第一版建议只维护一个后台应用和一个数据库，不提前拆多个服务。

- 后台应用：提供页面接口，执行登录与权限校验，接收 Teambition 变更，读取表单记录，计算管理数据并安排通知。
- 数据库：保存已确认配置、任务当前状态、反馈与状态历史、待执行任务、通知处理结果及审计。
- 后台定时任务：与应用共同部署，任务状态放数据库；应用重启后可继续未完成任务。不只靠进程内存记住哪些消息已发过。
- 独立备份位置：备份不能只放在应用同一台机器上。数据库、必要附件、配置和恢复步骤分别列清；密钥按公司要求加密管理，不进入代码仓库或普通审计。

不在本阶段引入额外消息队列、容器集群、独立分析平台或新的移动端。是否使用容器按公司现有运维方式决定。

### 网络访问建议

试运行后台先面向本人及明确指定的少量同事，四档权限在服务端执行。首阶段使用公司内网或公司 VPN，不购买域名，不开公网端口，不直接暴露本机数据库。电脑需保持运行，内网地址需固定或通过公司内部名称访问。后台页面入口与外部事件回调入口分别控制；员工访问保护方式不能导致平台回调无法接收，回调仍要验签和限定项目。

运行环境需要访问 Teambition、钉钉和 AI 表格接口。如果采用 Webhook，接收入口必须让 Teambition 服务端可访问，并校验签名、租户和项目范围。Teambition 云端通常不能直接访问公司私网 IP，不能把内网地址配置为云端可用回调。首阶段优先验证本机主动读取及对账；需要实时回调时，另行验证平台支持的接收方式或受控公网入口。公网 HTTPS、域名、证书、访问鉴权、带宽、服务地域及第三方数据通路暂不纳入首阶段。

## 4. 数据分别放在哪里

| 数据 | 原始或权威来源 | 本系统保存方式 |
| --- | --- | --- |
| 任务编号、标题、执行者、计划、父子关系和来源状态 | Teambition | 保存用于查询的当前状态和必要变更历史；记录同步时间与缺失情况 |
| 填写人原始提交 | AI 表格 | 按来源记录 ID 去重留存必要原始内容与平台身份、时间，记录处理结果 |
| 有效反馈与当前进度 | 本系统 | 保留每次处理历史；同任务按最新有效提交选当前值，不覆盖历史 |
| 版本纳入、状态语义、工作日历、人员映射、角色与权限 | 本系统 | 版本化或记录变更历史，服务端校验权限并留审计 |
| 风险、到期、并发和历史指标 | 本系统根据已确认规则计算 | 当前结果与来源关联；数据不全显示未知或异常 |
| 通知发出及待反馈提醒 | 本系统安排；AI 表格自动化执行通知动作 | 区分待发送、已交给平台、执行成功、明确失败和结果未知；保留唯一通知标识及对账信息 |
| 状态事件、同步运行和异常审计 | 来源事件与本系统操作 | 持久保存，不能依赖平台短期日志或进程内存作为唯一证据 |

任务使用稳定的内部 ID 做关联，用户界面显示 vkt-64 这类可见编号。来源状态 ID 与统一语义分开保存，不把状态名称写死。

当前状态按任务更新，不在每次轮询时复制所有工单形成一套新历史；仅在业务数据变化或审计需要时追加记录。容量估算分别计算任务数量、反馈数量、状态事件、审计及附件，不把它们混为一个“行数”。

## 5. 正常运行流程

1. 管理员配置人员映射、角色、系统权限、状态语义和工作日历，在后台选择需要纳入的版本。
2. 系统获取纳入范围内任务的当前事实，记录同步起点，不伪造起点前的开发与测试过程。
3. 来源变更事件触发更新，后台再读取权威当前值；定期检查差异，补齐漏同步。
4. 到采集时间，由系统核对任务资格和身份，生成通知任务，交给已确认的余莉个人发送自动化。不得改为其他个人或机器人代发而不确认。
5. 执行者打开任务反馈链接提交。后台读取新记录，校验真实身份、任务关系和内容，保留原始记录及处理结果。
6. 最新有效反馈更新当前展示；本轮采集起点之后的有效反馈结束本轮未发送的待反馈提醒。逾期催办按原规则重新计时，不能混为永久停止。
7. 已交给平台的消息与尚在后台等待的消息分开处理；平台能否及时撤销尚未验证，不能承诺反馈到达后所有已排队消息立即取消。
8. 任务或版本退出相关管理范围后按既定规则停止后续采集，保留历史和处理记录。

固定业务链接应关联稳定任务身份。任务改名、换执行者后，历史提交如何校验和旧链接预填如何更新，仍列正式实现测试，不沿用测试脚本的静态上下文作为完整方案。

## 6. 同步、失败与恢复建议

### 时效目标（建议值，不是已测保证）

- 日常看板和表单处理先按不超过 15 分钟的正常刷新目标设计，显示最近成功同步时间；是否适合当前配额及负载，需压测后确认。
- Webhook 可用时及时处理变化；每日至少安排一次纳入范围对账，失败时标记异常，不能把读取失败当空数据。
- 通知按已确认公司日历和采集时间安排；提交给平台后，平台排队和实际送达时间单独记录，不承诺秒级送达。
- 发送前再次核对任务资格和是否已有反馈，缩小误提醒窗口；仍需测试并发边界。

### 异常处理

- 来源接口暂时不可用：保留上次成功结果并显示时间、异常和影响范围；不显示为刚更新成功。
- 任务查询为空或无权限：标记需核实，不自动永久删除历史。
- 通知写入或发送结果不明：先对账，不盲目重发。只有明确失败且确认未发出的情况才进入受控重试，自动次数与间隔另外定稿。
- 余莉发送授权失效或个人不再具备资格：暂停相关发送并产生管理异常，不擅自替换发送人。
- 后台重启：从持久化任务及处理记录恢复；避免重复处理和重复通知。
- 原始反馈保留已拒绝记录，明确原因；存在风险等需要复核的内容不能凭测试脚本直接判定正式有效。

## 7. 数据备份与维护建议

建议首版每天备份数据库。用户目前没有机外存储，暂建议 F 盘主数据导出压缩到另一物理磁盘上的 C 盘，限制容量与保留份数；具体路径和策略尚未实施。该方案不能防整机损失或勒索软件，机外备份缺口继续保留。正式试用前至少完成一次恢复演练，验证不仅能备份，还能还原登录权限、配置、任务、反馈历史与通知处理状态。

本机试运行建议每天在电脑在线时备份，并明确显示最近一次成功备份时间；错过的备份须提示，不把计划执行当成成功。先以最多损失最近 24 小时内尚未备份的本系统数据、一个工作日内恢复作为讨论目标；目前无人值守，不能承诺已达到。须业务接受、恢复演练及维护方式确认后才成为验收标准。Teambition 和 AI 表格仍存在的来源数据可帮助补齐，但本系统独有配置、补录、审计及通知状态不保证能从来源重建。恢复后不得直接重放历史通知。

每日备份并不自动带来任意时刻恢复能力。若要求损失更少或更快恢复，需要单独评估连续备份、资源和费用。

PostgreSQL 官方提供 pg_dump 等备份工具；能否满足恢复目标仍取决于实际配置、备份范围和恢复演练。Supabase 官方对免费项目建议定期导出并保存异地备份，不能把历史讨论的免费方案当成已有备份保障。
