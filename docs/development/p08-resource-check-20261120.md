## 反馈查询性能修复

逐语句计时确认：每次重新校验逐条更新全部工单的当前值，产生大量数据库往返，并延长安全锁及反馈锁的持有时间。这是本次已证实的主要成本；不据此排除其他规模边界。

`app/feedback-state.mjs` 保留资格重新校验、原事务及锁顺序，将当前值合并为一条 `jsonb_to_recordset` 批量写入。旧当前值按稳定任务 ID 建立 Map，避免逐任务扫描旧值。没有增加业务超时、放松权限、减少历史或跳过资格校验。新增回归验证单次批量更新、缺失未知行重建及原值一致；原有同刻冲突、资格变化、复核和回滚回归继续执行。

主资源工具还记录了重建服务后的 `ECONNRESET`。重建探针改用标准库新连接，避免复用旧服务已关闭的 HTTP 连接；负载请求及失败断言保持原样。新增探针回归覆盖新连接和无效会话拒绝。旧失败报告保留，不回写为通过。

新增 `scripts/p08-history-growth-check.mjs`，仅使用已核对的隔离恢复库。保留活跃版本，另构造虚构历史版本，再分档增加修订及有效历史，检查并发查询和原当前值一致。历史数据通过有界 SQL 批次构造，只证明留存规模下的查询表现，不证明历史归档流程、真实采集吞吐、无限增长或长期办公体验。具体规模、失败及复测数值继续只留本机。

历史增长探测进一步暴露了查看单个版本仍全局重算的问题。反馈查看对已关联记录只重校验所选版本，并只更新该版本当前值；未关联记录继续按全局事实核对。来源同步、身份撤销、规则与映射变更等写入仍调用全局重新校验。未关联记录的稳定任务匹配继续使用全局任务集合，不能因为查询范围缩小就把跨版本重复编号误判为唯一任务。新增回归覆盖其他版本当前值不被查看操作更新、全局写入仍覆盖其他版本以及重复编号保持未关联。
